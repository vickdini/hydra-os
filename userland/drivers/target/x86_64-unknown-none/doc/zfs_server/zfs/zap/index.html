§ZFS Attribute Processor (ZAP) & Directories

§Subsystem Role & Architecture

This module provides the directory management implementation for Hydra’s OpenZFS filesystem layer. In OpenZFS, directories are specialized dnode objects whose data payload is formatted as variable-length directory entries structured within 4 KiB logical blocks.

§Architecture & Layout

A directory is an object whose data is a sequence of 4 KiB blocks of variable-length entry records. Records never cross a block boundary:

+--------+---------+----------+-------+----------------+---------+
| ino u64| len u16 | nlen u8  | type  | name[nlen]     | padding |
+--------+---------+----------+-------+----------------+---------+

len spans to the next record, so a record can carry free space after its name. Removing a record merges it into the previous record of its block (or zeroes ino when it is the first). An entry’s byte offset in the object never changes while it exists, which makes it a stable readdir cookie.

Lookups use an in-memory index (name -> entry), built on first access and cached.

§Key Types & Interfaces

  • DirEntry: Low-level directory record returned by Zap::readdir.
  • ZapEntry: Directory listing representation for user-space and shell commands.
  • Zap: Main engine managing directory indexing, lookup, insertion, and deletion.

§Concurrency & Hardware Semantics

Directory operations mutate DMU object blocks. Consistency is guarded at higher layers (ZPL / filesystem server mutexes) when committing transactional updates.
