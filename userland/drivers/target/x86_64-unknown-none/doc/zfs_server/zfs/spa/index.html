§Storage Pool Allocator (SPA)

§Subsystem Role & Architecture

The Storage Pool Allocator (SPA) is the bottom layer of Hydra’s OpenZFS implementation. It abstracts physical storage into a virtual device (Vdev), manages block allocation via a persistent space bitmap, maintains an in-memory physical frame cache (BlockCache), and controls the uberblock ring for atomic commit semantics.

§Crash Consistency & Transaction Groups

Blocks freed in transaction group N are still referenced by uberblock N-1, so they are only returned to the allocator after uberblock N is on disk, and only reach the on-disk bitmap in the commit of txg N+1. A crash can therefore leak blocks allocated by an unfinished commit, but never hands out a block the last valid uberblock still uses.

§Key Types & Interfaces

  • Vdev: The disk under the pool, driven by the Ring 3 disk driver (ata-driver), or a RAM disk.
  • BlockCache: LRU physical frame cache avoiding redundant device read cycles.
  • Spa: Storage Pool Allocator controlling allocation cursors, bitmaps, and labels.
  • DiskContents: Detection state for disk inspection prior to pool import.

§Concurrency & Hardware Semantics

The kernel has no disk driver of its own. Requests to the disk driver are calls to its service (crate::ipc::service::call), which run the driver in the caller’s place, so they may be made with the file system’s locks held. Allocations and frees are staged in transaction groups and committed atomically.
