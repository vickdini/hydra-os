Hydra OS — Source Code Documentation Standard

  • Document Version: 1.0.0
  • Scope: All Rust source files (src/**/*.rs) across the entire Hydra OS codebase.
  • Engine Compatibility: rustdoc (Rust 2021 Edition), Markdown (CommonMark), GitHub Flavored Markdown (GFM).
  • Primary Goal: Ensure every module, type, function, and unsafe block is maximally understandable, self-explanatory, and accessible to both systems engineers and learners.

1. Core Philosophy: "Code Tells How, Docs Tell Why"

  1. Self-Explanatory Architecture: Source code expresses the raw algorithmic logic; documentation articulates the architectural intent, hardware constraints, invariants, and safety prerequisites.
  2. Accessible Rigor: Use clear, accessible English accompanied by intuitive systems analogies (e.g., capability tokens as security keycards, frame allocator as parking lot attendant), while maintaining absolute technical precision regarding bit masks, memory layouts, and register states.
  3. Rustdoc First: All public items must compile cleanly into formatted HTML via cargo doc without broken links, unescaped HTML, or missing sections.
  4. No Trivial Comments: Comments like // sets the value or /// returns the id are forbidden. Every doc comment must provide genuine insight beyond what the type signature already conveys.

    /// Number of active reader file descriptors holding a reference to this pipe.
    readers: usize,
    /// Number of active writer file descriptors holding a reference to this pipe.

Build & Toolchain • Boot Sequence Order #03

Build Script Documentation

  • Source File: build.rs
  • Subsystem: Toolchain & Assembly Build Automation

1. Purpose & Context

In earlier phases or legacy configurations, Hydra supported a hybrid BIOS/Multiboot bootloader mode that required compiling 16-bit and 32-bit assembly files (header.asm, main.asm, main64.asm) with the nasm assembler before linking into ELF objects.

In current native UEFI builds, Cargo compiles Rust directly targeting x86_64-unknown-uefi without requiring external assembly compilation, with build = false in Cargo.toml.

2. Key Functions

assemble_file(file: &str, output_dir: &str)

  1. Checks the DEBUG environment variable to determine whether to emit DWARF debug symbols (-g).
  2. Invokes nasm to compile an .asm source file into an ELF64 object (.o).
  3. Instructs Cargo to re-run the build script if the source assembly file changes (cargo:rerun-if-changed).
  4. Tells the Rust linker to link the resulting object file (cargo:rustc-link-object).

assemble_all(output_dir: &str)

Loops through the standard assembly boot files: - boot/header.asm: Multiboot2 header definition. - boot/main.asm: 32-bit protected mode entry point, page table setup, and long mode switch. - boot/main64.asm: 64-bit trampoline to Rust entry point.

Stage 0: Firmware Handoff • Boot Sequence Order #04

Legacy Assembly Bootstrapper Documentation

  • Source Directory: src/arch/x86_64/boot/
  • Files:
  • header.asm
  • main.asm
  • main64.asm
  • Subsystem: Architecture / Legacy BIOS Boot Trampoline

1. Overview

Before migrating to native UEFI, x86 PCs booted via legacy BIOS. Under BIOS: 1. The CPU boots in 16-bit Real Mode. 2. A bootloader (like GRUB) loads the kernel into 32-bit Protected Mode. 3. The kernel itself is responsible for setting up initial page tables, enabling PAE, switching to 64-bit Long Mode, and jumping to 64-bit code.

These assembly files implement that transition for reference or hybrid BIOS/GRUB boot media.

2. File Breakdown

1. header.asm (Multiboot2 Header)

  • Defines the magic numbers and architecture tags required by Multiboot2-compliant bootloaders (such as GRUB).
  • Allows GRUB to recognize the kernel file as bootable.

2. main.asm (32-Bit to 64-Bit Transition)

  • Stack Initialization: Allocates an initial boot stack.
  • CPU Checks:
  • check_multiboot: Verifies that the bootloader passed the expected Multiboot magic value in EAX.
  • check_cpuid: Verifies that the CPU supports the cpuid instruction.
  • check_long_mode: Queries CPUID to verify 64-bit Long Mode hardware support.
  • Identity Paging: Configures an initial 2 MiB identity-mapped page table so memory addresses map 1:1 during the switch.
  • Enabling Long Mode: Sets the Physical Address Extension bit (PAE) in CR4, enables Long Mode in the Extended Feature Enable Register (EFER MSR), and enables Paging in CR0.
  • GDT Setup: Loads a temporary 64-bit code segment and performs a far jump to long_mode_start.

3. main64.asm (64-Bit Trampoline)

  • Re-zeros data segment registers (DS, ES, FS, GS, SS).
  • Invokes the Rust 64-bit entry point (call kernel_main).
  • Halts the CPU if the function ever returns.
Stage 1: Kernel Entry Point • Boot Sequence Order #05

Kernel Entry Point & Bootstrapping Documentation

  • Source File: src/main.rs
  • Subsystem: Microkernel Bootstrap & Initialization Orchestrator

1. Conceptual Overview

src/main.rs is the primary entry point executed when the UEFI firmware finishes hardware Power-On Self-Test (POST) and transfers control to BOOTX64.EFI.

Because Hydra targets native 64-bit UEFI directly: - The CPU is already in 64-bit Long Mode. - Paging is enabled by the UEFI firmware. - The kernel receives a valid uefi::prelude::SystemTable reference, enabling it to access firmware services before taking full ownership of the machine.

Global Descriptor Table (GDT) & TSS Documentation

  • Source File: src/arch/gdt.rs

1. Conceptual Overview

On x86_64 processors, the Global Descriptor Table (GDT) is a legacy hardware structure that remains vital for two critical operating system responsibilities: 1. Privilege Levels (Rings): Defining segments for Ring 0 (Kernel Mode) and Ring 3 (Userland Mode). 2. Task State Segment (TSS): Defining emergency hardware stack pointers for CPU privilege transitions and catastrophic fault recovery (Double Faults).

Privilege Rings

  • Ring 0: Full CPU privilege. The kernel executes here and can run privileged instructions (cli, sti, invlpg, write to control registers CR0..CR4).
  • Ring 3: Sandboxed user mode. Applications run here and are restricted by the MMU and capability system.

2. Architecture & Components

| 1. Kernel Code Segment (64-bit, Privilege Level 0)          |
| 2. Kernel Data Segment (Privilege Level 0)                  |
| 3. User Data Segment   (Privilege Level 3)                  |
| 4. User Code Segment   (64-bit, Privilege Level 3)          |
| 5. TSS Segment         (Task State Segment Descriptor)      |

               +-------------------------------+

3. Data Structures & Stacks

Stack Allocation

const STACK_SIZE: usize = 4096 * 5; // 20 KiB

Interrupt Descriptor Table (IDT) & Hardware Exceptions

  • Source File: src/arch/idt.rs
  • Subsystem: Architecture / CPU Exception Handling & Interrupt Routing

1. Conceptual Overview

The Interrupt Descriptor Table (IDT) is the x86_64 CPU hardware mechanism that dictates how the processor responds to asynchronous interrupts and synchronous software/hardware exceptions.

Each entry in the table is a 16-byte gate descriptor defining: 1. Target Handler Address: The 64-bit instruction pointer (RIP) to jump to when the vector fires. 2. Segment Selector: The GDT code segment selector (Hydra Ring 0 Kernel Code Segment). 3. Gate Type & DPL: Descriptor Privilege Level (DPL 0 for kernel-only hardware exceptions; DPL 3 for userland-callable traps like int3). 4. Interrupt Stack Table (IST): Optional alternate stack pointer index (1..=7) in the TSS, ensuring critical faults execute on guaranteed uncorrupted stack frames.

+----------------------------------------------------------------------------+
|                   CPU Interrupt Descriptor Table (IDT)                     |
+----------------------------------------------------------------------------+
| Vector 0..31  : CPU Hardware Exceptions (#DE, #DB, #BP, #UD, #DF, #GP, #PF)|
| Vector 32..47 : Legacy Hardware IRQs (PIC / IO-APIC)                       |
| Vector 48..255: APIC Timers, IPIs, Inter-Core Signaling, System Traps      |
+----------------------------------------------------------------------------+
                                     |
                                     v
                       [Assembly Trampoline Layer]
                                     |
                                     v
                   [Rust Dispatcher: hydra_exception_handler]

+-------------------------------------------+-------------------------+

+-----------+---+------+-----+------+------+-------------------------+
| Offset    | P | DPL  |  0  | Type | 000  | IST  | GDT Selector | Offset 15..0 |
|  31..16   |   |      |     | 1110 |      |      |              |              |

3. Trampoline Layer & Calling Convention

Hardware Exception Frame Variations

When a CPU exception occurs: - Some exceptions push an Error Code automatically (#DF, #TS, #NP, #SS, #GP, #PF, #AC). - Other exceptions push no Error Code (#DE, #DB, #BP, #OF, #UD, #NM).

To provide a uniform C-compatible context to Rust, assembly macros dynamically push a dummy zero for exceptions that lack hardware error codes:

.macro TRAP_NO_ERRCODE name, vec
.global \name
\name:
    push 0                  // Dummy error code
    push \vec               // Vector number
    jmp common_trap_handler
.endm

.macro TRAP_ERRCODE name, vec
.global \name
\name:
    push \vec               // Vector number (error code already pushed by CPU)
    jmp common_trap_handler
.endm

Stack Frame (ExceptionContext)

The assembly trampoline pushes all 15 general-purpose registers, creating a complete ExceptionContext:

    pub r15: u64, pub r14: u64, pub r13: u64, pub r12: u64,
    pub rbp: u64, pub rbx: u64, pub r11: u64, pub r10: u64,
    pub r9:  u64, pub r8:  u64, pub rdi: u64, pub rsi: u64,

UEFI & SysV Calling Convention Compatibility

Because Hydra targets UEFI (x86_64-unknown-uefi) while maintaining Unix microkernel foundations, the dispatcher assembly sets up argument passing for both conventions simultaneously:

    mov rcx, rsp            // 1st argument in Microsoft x64 / UEFI ABI
    mov rdi, rsp            // 1st argument in System V AMD64 ABI
    sub rsp, 32             // Allocate 32-byte shadow store (Win64) & align stack
    call hydra_exception_handler
    add rsp, 32             // Deallocate shadow store
    pop r15..rax            // Restore registers
    add rsp, 16             // Clean up vector and error code
    iretq                   // Return from interrupt

4. Exception Handlers

Vector 3: Breakpoint (#BP)

  • DPL: 3 (Permits Ring 3 userland processes to trigger software breakpoints with int3).
  • Behavior: Non-fatal diagnostic trap. Prints RIP, RFLAGS, and RSP, then resumes execution via iretq.

Vector 8: Double Fault (#DF)

  • IST: Linked to TSS IST index 1 (DOUBLE_FAULT_STACK).
  • Behavior: Even if the kernel stack overflows or suffers memory corruption, the hardware forcibly switches to a dedicated 20 KiB emergency stack, preventing immediate triple-fault reboot loops.

Vector 13: General Protection Fault (#GP)

  • Behavior: Decodes selector indices and privilege boundary violations.

Vector 14: Page Fault (#PF)

  • Behavior: Reads the faulting linear memory address from hardware control register CR2 (Cr2::read_raw()), and decodes the error code flags:
  • P (Bit 0): Non-present page (0) vs Page-level protection violation (1).
  • W/R (Bit 1): Read access (0) vs Write access (1).
  • U/S (Bit 2): Supervisor mode (0) vs User mode (1).
  • I/D (Bit 4): Data access (0) vs Instruction fetch (1).

8259 Programmable Interrupt Controller (PIC)

1. Architectural Role

The 8259 Programmable Interrupt Controller (PIC) is the legacy interrupt routing hardware in standard PC/AT architectures. It aggregates up to 15 hardware IRQs (Interrupt Request lines) across two cascading controllers and forwards them to the CPU via the INTR line.

In standard x86 BIOS systems, hardware IRQs initially collide with CPU exception vectors (0x00–0x1F). Hydra remaps the dual-PIC controllers to vectors 0x20–0x2F upon hardware takeover (exitboot), ensuring clear separation between CPU faults and hardware peripherals.

2. Port & Vector Mapping

Controller Command Port Data Port Vector Range IRQ Lines
Master PIC 0x20 0x21 0x20..0x27 (32..39) IRQ 0..7 (Timer, PS/2 Keyboard, Cascade, etc.)
Slave PIC 0xA0 0xA1 0x28..0x2F (40..47) IRQ 8..15 (RTC, ACPI, Primary/Secondary ATA)

3. Initialization & Remapping Sequence

Initialization uses a sequence of 4 Initialization Command Words (ICWs):

ICW1 (0x11): Start initialization in cascade mode, expect ICW4
   │
   ├─► ICW2: Set base vector offset
   │     Master = 0x20 (32)
   │     Slave  = 0x28 (40)
   │
   ├─► ICW3: Cascade wiring setup
   │     Master: bit 2 = 1 (Slave attached at IRQ 2)
   │     Slave : cascade identity 0x02
   │
   └─► ICW4 (0x01): 8086/88 operation mode

4. Interrupt Masking & End of Interrupt (EOI)

  • Default Masks:
  • Master Mask: 0xF8 (Unmasks IRQ 0 Timer, IRQ 1 Keyboard, IRQ 2 Cascade).
  • Slave Mask: 0xFF (All slave IRQs masked).
  • End of Interrupt (EOI):
  • When an interrupt is serviced, an EOI byte (0x20) must be written to the PIC command port.
  • If the IRQ originated from the Slave PIC (irq >= 8), an EOI must be sent to both Slave (0xA0) and Master (0x20).

8254 Programmable Interval Timer (PIT)

1. Architectural Role

The Intel 8254 Programmable Interval Timer (PIT) provides Hydra with a hardware clock source for measuring wall-clock time, coordinating preemptive multitasking ticks, and executing low-power sleeps.

The oscillator operates at an input frequency of 1,193,182 Hz (~1.193182 MHz). Channel 0 is wired directly to IRQ 0 on the Master PIC.

2. Configuration & Ports

  • Port 0x40: Channel 0 Data Port (read/write counter divisor)

Hydra configures Channel 0 in Mode 3 (Square Wave Generator): - Command Byte: 0x36 (00 Channel 0 | 11 Access lo/hi byte | 011 Mode 3 | 0 16-bit binary) - Target Frequency: 100 Hz (10 ms per tick) - Divisor: 1193182 / 100 = 11932 (0x2E9C)

3. Tick Counter & Low-Power Halts

Hardware Takeover & ExitBootServices

  • Source File: src/arch/boot_services.rs
  • Subsystem: Architecture / Hardware Ownership & UEFI Termination

1. Conceptual Overview

Operating systems that boot via UEFI start their existence in a hybrid environment: the processor is in 64-bit Long Mode, but the firmware retains partial control over memory allocation, display devices, and the system timer via UEFI Boot Services.

To become a true, self-governing microkernel, Hydra OS must execute the Hardware Takeover Sequence by calling the UEFI specification's terminal function: ExitBootServices.

Once ExitBootServices succeeds: 1. Firmware Eviction: All UEFI boot-time protocols, memory allocators, and event timers cease execution immediately. 2. Hardware Reconfiguration: The kernel assumes exclusive control over the Global Descriptor Table (GDTR), Task State Segment (TR), Interrupt Descriptor Table (IDTR), and Page Table Root (CR3). 3. Autonomous Driver Transition: Console output routes directly to Hydra's hardware GOP linear framebuffer (VideoConsole), and keyboard input routes directly to the physical 8042 PS/2 keyboard controller.

|  2. Switch Input to 8042 PS/2 Controller Driver (Ports 0x60/0x64)               |

|  7. Switch CPU CR3 to Hydra Autonomous PML4 Table (conventional RAM)            |

2. Hardware Takeover Pipeline

Step 1: Autonomous Video & Keyboard Activation

Before firmware protocols are severed, Hydra switches console routing:

The firmware validates the memory map key, frees internal boot-service structures, and hands unconditional hardware control to Hydra.

Step 3: GDT & Segment Reload (load_and_switch)

In 64-bit mode, the Code Segment (CS) cannot be reloaded using mov cs, ax. Hydra uses a far return (retfq) trampoline to reload CS with 0x08:

    push {sel}              // Kernel Code Selector (0x08)
    lea {tmp}, [2f + rip]   // Return RIP
    push {tmp}
    retfq                   // Far return: pops RIP then CS
2:
    mov ds, 0x10
    mov ss, 0x10
    ltr {tss_sel}           // Load Task Register with 0x28

Step 4: TSS IST Attachment on Double Fault

With the Task Register (TR) loaded with Hydra's TSS, the IDT entry for Double Fault (#DF, vector 8) is linked to IST index 1:

idt.entries[8].set_ist(1);

Any catastrophic kernel stack overflow will now switch immediately to Hydra's dedicated 20 KiB emergency stack.

Step 5: Autonomous CR3 Switch

Hydra switches the processor's Page Map Level 4 root from the firmware's PML4 table to Hydra's autonomous PML4 table:

KERNEL_SPACE.lock().switch();

CPU Control & Register Diagnostics Documentation

  • Source File: src/arch/cpu.rs
  • Subsystem: Architecture / CPU Control Registers

1. Conceptual Overview

On x86_64 processors, the processor's operating mode, memory translation mechanisms, and security features are governed by specialized Control Registers (CR0, CR2, CR3, CR4):

  • CR0: Controls basic execution features: Protected Mode, Paging enable, Write Protect (prevents kernel from inadvertently overwriting read-only user pages).
  • CR2: Stores the linear virtual address that triggered the most recent Page Fault exception. Vital for demand paging and memory debugging.
  • CR3: Points to the base physical address of the Level 4 Page Table (PML4). Loading a new value into CR3 immediately switches active virtual address spaces.

Ring 3 User Mode & Hardware System Calls (syscall / sysretq)

Overview

Phase 3 introduces hardware-enforced CPU privilege rings and the fast system call interface to Hydra OS. In long mode x86_64, the kernel transitions from pure kernel-mode threads (Ring 0) to unprivileged user processes executing at Current Privilege Level 3 (Ring 3).

The boundary between userland and the microkernel is guarded by: 1. Model-Specific Registers (MSRs): IA32_EFER.SCE, IA32_STAR, IA32_LSTAR, and IA32_FMASK configuring the hardware syscall and sysretq instructions. 2. Task State Segment (TSS) Privilege Stack (RSP0): Ensuring hardware interrupts and exceptions originating from Ring 3 safely pivot to a trusted per-task kernel stack. 3. 4-Level Paging Protection (USER_ACCESSIBLE): Granular page table permissions separating supervisor-only memory from user-accessible memory. 4. Hardware Fault Isolation: Intercepting user-mode General Protection Faults (#GP) and Page Faults (#PF) to terminate offending processes without compromising kernel stability.

The core implementation is split across: - Syscall MSRs & Assembly Dispatcher: src/arch/syscall.rs - Userland Syscall Library: src/syscall/user.rs - GDT & TSS RSP0 Configuration: src/arch/gdt.rs - Page Table User Accessibility: src/memory/paging.rs - Process Spawning & Preemption: src/task/scheduler.rs - Shell Diagnostics: src/shell/commands/task_cmds.rs

Model-Specific Registers (MSR) Configuration

During hardware takeover in src/arch/boot_services.rs, the kernel programs the four architectural system call MSRs via crate::arch::syscall::init():

MSR Address Register Name Configured Value Description
0xC0000080 IA32_EFER Bit 0 (SCE = 1) System Call Extensions: Enables the syscall and sysretq instructions in 64-bit mode.
0xC0000081 IA32_STAR 0x0013_0008_0000_0000 Segment Selectors: Bits [47:32] set Kernel CS to 0x08 (Kernel SS auto 0x10). Bits [63:48] set User base to 0x13, causing sysretq to load User SS = 0x1B (0x13+8) and User CS = 0x23 (0x13+16).

Assembly Syscall Trampoline (asm_syscall_entry)

Because the x86_64 syscall instruction does not switch the stack pointer (RSP), the CPU enters kernel mode with RSP still pointing into untrusted user space. The assembly trampoline immediately pivots to the task's kernel stack before saving registers:

.global asm_syscall_entry
asm_syscall_entry:
    // 1. Preserve user RSP in scratch and switch to current task kernel stack
    mov [rip + USER_RSP_SCRATCH], rsp
    mov rsp, [rip + CURRENT_KERNEL_RSP]

    // 2. Build SyscallFrame on kernel stack
    push qword ptr [rip + USER_RSP_SCRATCH] // User RSP
    push r11                                // User RFLAGS
    push rcx                                // User RIP
    push rbx
    push rbp
    push r12
    push r13
    push r14
    push r15
    push rax                                // Syscall number
    push rdi                                // Arg 0
    push rsi                                // Arg 1
    push rdx                                // Arg 2
    push r10                                // Arg 3
    push r8                                 // Arg 4
    push r9                                 // Arg 5

    // 3. Call Rust dispatcher (passes &mut SyscallFrame in RCX and RDI)
    mov rcx, rsp
    mov rdi, rsp
    sub rsp, 48
    call hydra_syscall_dispatcher
    add rsp, 48

    // 4. Restore registers and user stack
    pop r9
    pop r8
    pop r10
    pop rdx
    pop rsi
    pop rdi
    pop rax                                 // Syscall return value in RAX
    pop r15
    pop r14
    pop r13
    pop r12
    pop rbp
    pop rbx
    pop rcx                                 // Restore User RIP
    pop r11                                 // Restore User RFLAGS
    pop rsp                                 // Restore User RSP directly

    // 5. Return to unprivileged Ring 3
    sysretq

Task State Segment (TSS) & Interrupt Stack Switching

When a hardware interrupt (such as IRQ 0 PIT timer or IRQ 1 keyboard) or a CPU exception (#GP, #PF) fires while running in Ring 3: 1. The CPU hardware reads RSP0 from the active TSS (privilege_stack_table[0]). 2. The hardware switches RSP to RSP0. 3. The hardware pushes SS (0x1B), RSP (user stack), RFLAGS, CS (0x23), RIP, and error code onto the task's kernel stack. 4. The interrupt routine runs safely in Ring 0. 5. Upon returning, iretq automatically pops the user context and drops back to Ring 3.

Whenever the scheduler performs a context switch in src/task/scheduler.rs, it synchronizes both hardware stack pointers:

// Update hardware TSS RSP0 and SYSCALL kernel RSP for the incoming task

Physical Memory & Frame Allocator Documentation

  • Source File: src/memory/frame_allocator.rs

1. Conceptual Overview

When a computer boots up, its physical Random Access Memory (RAM) is not one continuous empty space. Certain chunks are occupied by motherboard ROM, video graphics RAM, ACPI tables, and UEFI firmware code.

The Physical Memory Frame Allocator is responsible for: 1. Asking UEFI firmware which memory regions are safe and usable (CONVENTIONAL memory). 2. Dividing that usable RAM into standard 4096-byte (4 KiB) chunks, called Physical Frames. 3. Handing out frames one-by-one to the kernel when it needs memory for page tables, stacks, or user processes.

The Real-World Analogy

Think of RAM as a vast parking lot: - Some spots are reserved for emergency vehicles or building infrastructure (firmware/hardware). - The Physical Memory Manager is the parking attendant with a map of all standard open spots. - Whenever a driver (a process or page table) arrives, the attendant assigns them the next available numbered spot (0x1000, 0x2000, etc.).

Virtual Memory & Paging Documentation

  • Source File: src/memory/paging.rs
  • Subsystem: Memory Management (Virtual Layer & Hardware MMU)

1. Conceptual Overview

Modern 64-bit CPUs do not let user programs or high-level kernel functions read and write directly to physical RAM chips. Instead, they use Virtual Memory.

Every address a program interacts with is a Virtual Address. The hardware Memory Management Unit (MMU) consults a multi-level tree of translation tables (called Page Tables) to convert that virtual address into a Physical Address in RAM.

Benefits of Paging

  1. Isolation: Process A and Process B can both have code at virtual address 0x400000, but they map to completely different physical RAM chips.
  2. Protection: Pages can be marked read-only, non-executable (NX/XD bit to prevent malware buffer-overflow attacks), or kernel-only.
  3. Continuity: Large buffers appear contiguous in virtual memory even if physical frames are scattered across RAM.

2. 4-Level Paging Architecture (x86_64)

In 64-bit x86 architecture, translating a 48-bit canonical virtual address uses a 4-level tree:

Virtual Address:
[ PML4 Index (9 bits) | PDPT Index (9 bits) | PD Index (9 bits) | PT Index (9 bits) | Offset (12 bits) ]
        |                      |                     |                  |                     |
        v                      v                     v                  v                     v
   [ CR3 Register ]
        |
        +---> PML4 Table (Level 4)
                  |
                  +---> PDPT Table (Level 3 - Page Directory Pointer Table)
                            |
                            +---> PD Table (Level 2 - Page Directory)
                                      |
                                      +---> PT Table (Level 1 - Page Table)
                                                |
                                                +---> Physical Frame (4 KiB) + Offset
  • CR3: The CPU control register holding the physical address of the active Level 4 (PML4) table.

Capability Subsystem Overview

  • Source File: src/capability/mod.rs
  • Subsystem: Capability-Based Security

1. Conceptual Overview

Traditional operating systems (like standard Linux or Windows) often rely on Access Control Lists (ACLs) or ambient authority (e.g., "this process runs as root/administrator, so it can touch anything"). If an administrative process has a bug or is hijacked, the entire system is compromised.

Hydra uses Capability-Based Security (similar to seL4 and Fuchsia Zircon).

The Real-World Analogy

Think of a Capability as a non-forgeable, digital smart keycard: - You cannot just claim "I am the administrator". - You can only perform an operation if you hold a specific keycard that explicitly grants the right to perform that action on that exact resource. - You can hand a copy of a keycard with restricted permissions to another process (e.g., giving someone a key that allows reading a file, but not modifying or deleting it).

2. The Rights Bitflags

Rights defines what actions a process holding a capability is permitted to execute:

#[derive(Debug, Clone, Copy, PartialEq, Eq)]

Flag Value Description
Rights::READ 1 << 0 (1) Permission to inspect data in the target object.
Rights::WRITE 1 << 1 (2) Permission to modify or overwrite the target object.
Rights::EXECUTE 1 << 2 (4) Permission to execute machine instructions from the object (memory frame).
Rights::GRANT 1 << 3 (8) Permission to delegate, duplicate, or transfer this capability to another process.
Rights::CALL 1 << 4 (16) Permission to invoke or call an IPC Endpoint.
Rights::ALL 0x1F (31) Full combined permissions (READ \| WRITE \| EXECUTE \| GRANT \| CALL).

1. Conceptual Overview

In Hydra, userland processes cannot store raw pointers to kernel objects or hardware devices. Instead, the kernel maintains a Capability Table (also known as a CSpace or CNode) on behalf of each process.

The Real-World Analogy

Think of a Capability Table like a keyring or safe-deposit locker: - The process holds numbers (slots: 0, 1, 2, ...). - When a process asks the kernel, "Read from memory at Slot 3", the kernel checks Slot 3 in that process's Capability Table. - If Slot 3 contains a valid capability and includes Rights::READ, the kernel performs the operation. - If the slot is empty or lacks the required right, the kernel immediately denies the request. - The process never touches the raw physical address or hardware pointer directly, preventing spoofing and unauthorized access.

  • slots: Fixed array of 256 optional capability slots.
  • next_free_slot: Circular search cursor to quickly find available slots upon insertion.

CapabilityTable::new() -> Self

Creates a new, empty capability table where all 256 slots are None.

IPC Message Module Documentation

  • Source File: src/ipc/message.rs
  • Subsystem: Microkernel IPC (Inter-Process Communication)

1. Conceptual Overview

In a microkernel operating system like Hydra, core operating system services (such as file systems, network drivers, and device managers) run as separate, isolated programs rather than inside a single monolithic kernel. Because these isolated programs cannot directly access each other's memory, they must communicate by sending Messages across a secured boundary.

The Real-World Analogy

Think of an IPC Message like a registered letter or courier package: 1. The Label (label): The subject line or action request (e.g., "Read File", "Get Time", "Allocate Memory"). 2. The Fast Payload (args): A quick handwritten note with up to 4 numbers or pointers that fit directly into the CPU's registers for high-speed delivery without touching RAM. 3. The Enclosed Key/Passport (capability): An optional security token granted to the receiver, giving them special permission to access a specific memory buffer, device, or channel.

2. Architecture & Data Structures

+-------------------------------------------------------------+
|                        Message                              |
+-------------------------------------------------------------+
| label: u32                | Protocol / Syscall ID           |
| args: [u64; 4]            | Up to 4 fast 64-bit parameters  |
| capability: Option<Cap>   | Optional transferred security   |
|                           | token / permission              |
+-------------------------------------------------------------+

Constants

  • MAX_INLINE_WORDS: usize = 4: The number of 64-bit arguments (u64) carried directly within a message. Using 4 words (32 bytes) allows the microkernel to transfer arguments directly using CPU registers (such as RDI, RSI, RDX, RCX on x86_64), making IPC fast.

3. The Message Struct

#[derive(Debug, Clone, Copy)]
pub struct Message {
    pub label: u32,
    pub args: [u64; MAX_INLINE_WORDS],
    pub capability: Option<Capability>,
}

Fields Explained

Field Type Description
label u32 An operation code indicating what action is requested (e.g. 0x1001 for ping, 0x2001 for read).
args [u64; 4] Array of 4 inline 64-bit numbers. Can be integers, memory offsets, or byte lengths.
capability Option<Capability> An optional security token transferred along with the message to delegate authority.

Message::new(label: u32) -> Self

1. Conceptual Overview

In a microkernel architecture, programs cannot talk directly to each other because their address spaces are completely isolated by the CPU's memory management unit (MMU). An Endpoint acts as a meeting place (rendezvous point) or postal mailbox managed by the kernel.

The Real-World Analogy

Imagine an apartment building where residents cannot enter each other's apartments: - An Endpoint is a secure PO Box in the lobby. - Process A drops a Message into the box (send). - Process B checks the box and retrieves the message (receive). - The kernel ensures only residents holding the correct security key (Capability) can post or retrieve items from that specific box.

2. Architecture & Data Structures

                 |         SharedEndpoint (Mutex)          |
                 +-----------------------------------------+
                                      |
                                      v
  [Process A] ---> send() --->  [ Ring Buffer ]  ---> receive() ---> [Process B]
  (Sender)                       Slots: 0..16                         (Receiver)

Queue Parameters

3. Struct Details

Endpoint

The core internal endpoint managing a circular ring buffer of messages.

    id: u32,

    tail: usize,
    count: usize,
}

  • buffer: Fixed-size array holding pending messages without needing dynamic heap allocations.
  • head: Read pointer pointing to the next message to be consumed (FIFO order).
  • tail: Write pointer pointing to the next free slot for an incoming message.
  • count: Current number of queued, unread messages.

Indicates the scheduling and readiness state of the communication channel:

    Idle,
    Active,

SharedEndpoint

A thread-safe wrapper around Endpoint using a spin::Mutex. This allows concurrent threads and interrupts to safely send and receive messages without race conditions.

Endpoint::new(id: u32) -> Self

Initializes a new empty message queue with the specified ID.

Endpoint::send(&mut self, msg: Message) -> Result<(), &'static str>

Constructs a new mutex-protected endpoint.

SharedEndpoint::id(&self) -> u32

Returns the ID of the wrapped endpoint.

1. Architectural Motivation

In traditional monolithic operating systems, the filesystem runs in kernel space (Ring 0) with direct block device access. This violates principle-of-least-privilege and microkernel design tenants. 2. ZFS Core Architecture

Hydra's ZFS implementation faithfully models the fundamental layers of OpenZFS:

1. Storage Pool Allocator (SPA)

  • Storage Pool: Named hydrapool by default.
  • VDEV (Virtual Device): Manages physical block storage or memory-backed frames.
  • Copy-on-Write (CoW): Data blocks are never updated in-place. Writing allocates new blocks, preserves previous data for snapshots, and links to a new Merkle root.
  • Active Uberblock: The root of the storage pool (magic: 0x00bab10c, version: 5000). Every write transaction commits an incremented Transaction Group (TXG).

2. Fletcher-4 End-to-End Checksums

Every block pointer (blkptr_t) carries a 256-bit Fletcher-4 checksum (4 parallel 64-bit accumulators): $$\text{Fletcher-4: } a = \sum w_i, \quad b = \sum a_i, \quad c = \sum b_i, \quad d = \sum c_i$$ Upon read operations, the ZFS File Server recalculates the checksum and detects any silent data corruption before returning data to the caller.

3. Data Management Unit (DMU) & Dnodes

  • Objects in ZFS are represented by DnodePhys structures (obj_type, block size, file size, direct block pointers).
  • Supported Object Types:
  • PlainFile: Data payload blocks.
  • Directory: Associated with a ZAP object.
  • Dataset: Isolated filesystem namespace (hydrapool/root, hydrapool/bin).
  • MasterNode: Meta-Object Set (MOS) root.

4. ZFS Attribute Processor (ZAP)

  • Micro-ZAP structure indexing directory entries (mapping string filenames to object IDs).
  • Enables $O(1)$ file lookups inside datasets.

ZFS_IPC_READ 0x3003 [obj_id, dest_buf_ptr, max_len, 0] [status, bytes_read, txg, 0] Reads and checksum-verifies file data.

Task Control Block (TCB) & Thread State

Overview

The Task Control Block (Task / TCB) forms the foundational abstraction of thread execution and process representation in the Hydra 64-bit microkernel. Each execution thread is managed through an independent TCB that encapsulates its unique 64-bit identifier (TaskId), descriptive thread label, lifecycle execution state (TaskState), scheduling priority (TaskPriority), architectural register frame (TaskRegisters), dedicated 16 KiB execution stack, CPU tick consumption statistics, and an isolated per-task capability security space (CapabilityTable).

The implementation is located in src/task/tcb.rs with public re-exports in src/task/mod.rs.

Context Synchronization

Two symmetric methods bridge the gap between hardware interrupt frames and the kernel's scheduler data structures:

  1. save_from_context(&mut self, ctx: &ExceptionContext, cr3: u64): Captures the running thread's state directly from the stack-saved ExceptionContext created by the assembly interrupt gate trampoline, recording the current CR3 paging root.

  2. restore_to_context(&self, ctx: &mut ExceptionContext): Transfers the incoming thread's register frame into the active interrupt context frame on the stack. When the hardware interrupt routine exits via iretq, the CPU immediately restores all general-purpose registers and atomically resumes execution inside the new task.

Running Thread currently owns the CPU core and is executing instructions. Selected by the scheduler during context switch.
Sleeping { wake_tick } Thread is suspended until the hardware PIT tick counter reaches wake_tick. Invocation of sleep_ms() or sleep_ticks().
Blocked Thread is waiting on a capability-mediated IPC message or resource lock. Synchronous IPC rendezvous request.
Dead Thread has finished execution or was explicitly terminated by PID. Invocation of exit() or administrative kill().

Task Priority Levels (TaskPriority)

Hydra supports three distinct priority strata:

  1. High (Priority 2): Time-critical device drivers and real-time event handlers.
  2. Normal (Priority 1): Standard userland processes, shell sessions, and background workers.
  3. Idle (Priority 0): Lowest priority; assigned exclusively to Task 1 (idle). It is only scheduled when no other Ready thread exists in the system.

Memory Footprint Optimization & Stack Safety

  • Heap-Allocated CSpace: The CapabilityTable provides 256 capability slots (~8 KiB). In early designs, allocating this structure inline inside Task by value resulted in stack overflows during task creation. By storing cspace: Box<CapabilityTable>, the memory footprint of Task on the stack is reduced from 8,256 bytes to ~168 bytes, guaranteeing zero stack smashing during deep call chains.
  • Dedicated 16 KiB Kernel Stacks: Newly spawned threads allocate 16,384 bytes (16 KiB) on the 8 MiB kernel heap. The top of the stack is 16-byte aligned ((stack_top & !0xF)), and an initial 48-byte shadow space offset is reserved to satisfy Microsoft x64 / UEFI and SysV AMD64 calling convention requirements.

Preemptive Multitasking & Context Switching

Overview

The Hydra multitasking subsystem implements a preemptive round-robin scheduler driven by the 8254 Programmable Interval Timer (PIT) firing at 100 Hz on IDT Vector 32 (IRQ 0). Multitasking enables concurrent execution of independent kernel threads, background worker tasks, and the interactive shell with transparent hardware context switching.

The implementation resides in src/task/scheduler.rs, with the public API exposed through src/task/mod.rs and interactive shell commands in src/shell/commands/task_cmds.rs.

Scheduling Architecture & Timeslicing

The scheduler operates on a fixed timeslice quantum of 5 PIT timer ticks (50 ms) at 100 Hz.

Scheduling Algorithm Details

  1. Sleep Accounting: On every tick, the scheduler scans all registered tasks and transitions any task in TaskState::Sleeping { wake_tick } back to TaskState::Ready if the current PIT tick count has reached or exceeded wake_tick.
  2. Timeslice Depletion: The currently running task has its ticks_run counter incremented and timeslice_remaining decremented. If more than 1 tick remains in its timeslice, the scheduler returns immediately without context switching.
  3. Round-Robin Selection: When the timeslice expires, the outgoing task's registers and CR3 paging root are saved from ExceptionContext. The run-queue is scanned in two passes: - Pass 1 (Normal & High Priority): Scans for the next runnable non-idle task (priority > Idle). - Pass 2 (Idle Fallback): If no normal tasks are ready, schedules Task 1 (idle) to execute low-power CPU halts (hlt).
  4. Context Switch Restoration: The chosen task's registers are written back into ExceptionContext, its timeslice is reset to 50 ms, and if the task has a distinct CR3 page table, the CPU paging root is updated via Cr3::write().

Hardware Context Switching via iretq

Hydra employs an in-place stack frame modification pattern for architectural context switching:

  1. When IRQ 0 fires, the CPU pushes SS, RSP, RFLAGS, CS, and RIP onto the active stack.
  2. The assembly entry point common_trap_handler pushes all fifteen general-purpose registers (RAX through R15) and points RSP to the ExceptionContext.
  3. SCHEDULER.lock().schedule(ctx) modifies the values stored inside the ExceptionContext on the stack.
  4. As common_trap_handler unwinds, pop r15..rax loads the incoming task's general-purpose registers.
  5. The hardware iretq instruction pops RIP, CS, RFLAGS, RSP, and SS. In 64-bit long mode, iretq unconditionally pops RSP and SS regardless of privilege level, atomically switching execution to the new task's stack and instruction pointer.

Task Trampoline & Calling Conventions

When a newly spawned kernel thread starts execution for the first time, it does not resume from a previously interrupted state. Instead, it enters through the Task Trampoline:

extern "C" fn task_trampoline(entry_fn_addr: usize) -> ! {
    let func: fn() = unsafe { core::mem::transmute(entry_fn_addr) };
    func();

    // Mark task Dead upon normal function exit and yield CPU
    crate::task::exit();
}

ABI Alignment & Register Conventions

  • Win64 vs SysV Dual Argument Passing: Under the UEFI target (x86_64-unknown-uefi), the Microsoft x64 calling convention passes the first function argument in RCX (in contrast to SysV AMD64, which uses RDI). spawn_internal initializes both regs.rcx and regs.rdi to the entry point address to guarantee cross-ABI compatibility.
  • Shadow Space & 16-Byte Stack Alignment: The initial stack pointer is configured as initial_rsp = stack_top.saturating_sub(48). This satisfies the mandatory 32-byte Microsoft x64 shadow spill space requirement and aligns the stack to a 16-byte boundary upon entry into func().

Microkernel Synchronization Primitives & Wait Queues

Overview

In Phase 4, Hydra OS activates the TaskState::Blocked lifecycle state in the scheduler and introduces true sleeping synchronization primitives. Unlike busy-wait spinlocks that burn CPU cycles, sleep-locks transition contended threads to a suspended state and deschedule them immediately. When the lock or resource becomes available, the wait-queue awakens the thread, returning it to TaskState::Ready.

The synchronization subsystem is implemented in src/sync/ and integrated with the preemptive scheduler in src/task/scheduler.rs and the IPC subsystem in src/ipc/endpoint.rs.

Core Primitives

1. Wait Queue (WaitQueue)

The WaitQueue maintains a FIFO queue of suspended tasks (TaskId) awaiting an event:

pub struct WaitQueue {
    waiters: VecDeque<TaskId>,
}
  • wait(&mut self): Captures the current TaskId, enqueues it, marks the task as TaskState::Blocked, and invokes yield_now() to relinquish the CPU immediately.
  • wake_one(&mut self) -> Option<TaskId>: Dequeues the oldest waiting task and transitions it to TaskState::Ready.
  • wake_all(&mut self) -> usize: Dequeues and unblocks all waiting tasks.

2. Sleeping Mutex (Mutex<T>)

The Mutex<T> provides mutual exclusion with automatic thread suspension:

pub struct Mutex<T> {
    locked: AtomicBool,
    owner: AtomicU64,
    waiters: SpinLock<WaitQueue>,
    data: UnsafeCell<T>,
}
  • Fast Path: Uncontended acquisition succeeds via atomic CAS (compare_exchange(false, true)), requiring zero context switches or allocations.
  • Contention Path: If already locked, the calling task registers in waiters, transitions to TaskState::Blocked, and yields the CPU.
  • Release: When the MutexGuard is dropped, ownership is cleared, and waiters.wake_one() is called to reschedule the next waiter.

3. Counting Semaphore (Semaphore)

The Semaphore manages shared permits: - acquire(): Atomically decrements permits. If no permits remain, the caller is enqueued in the semaphore's WaitQueue and suspended. - release(): Increments permits and awakens one waiting task from the queue.

4. Condition Variable (CondVar)

The CondVar enables threads to suspend execution until a condition predicate is satisfied: - wait(guard: MutexGuard<T>): Atomically releases the held mutex, enqueues the thread in the condition variable's wait queue, and blocks. When awakened, it re-acquires the mutex before returning. - notify_one(): Wakes a single waiting thread. - notify_all(): Wakes all waiting threads.

5. Synchronized Bounded Channel (Channel<T>)

The Channel<T> implements thread-safe message passing: - send(&self, item: T): Blocks if the channel buffer is at capacity until a receiver consumes data. - recv(&self) -> T: Blocks if the channel is empty until a sender transmits an item.

Blocking Inter-Process Communication (IPC)

In src/ipc/endpoint.rs, microkernel endpoints feature integrated send and receive wait queues:

  • receive_blocking() -> Message: Extracts a message, suspending the receiver if the queue is empty. Awakens any blocked senders.
  • System Endpoints (SYSTEM_ENDPOINTS[0..15]): Global shared rendezvous ports accessible both by kernel threads and user processes via SYS_IPC_SEND and SYS_IPC_RECV system calls.

Position-Independent Executables (PIE) & Segment Relocation

Hydra compiles userland binaries targeting x86_64-unknown-none with position-independent executable flags (ET_DYN). Because standard UEFI firmware utilizes identity mapping across the physical address space, fixed-address binaries (ET_EXEC at 0x400000) could collide with hardware-mapped MMIO or kernel structures.

For ET_DYN binaries: 1. The loader determines the virtual span required across all PT_LOAD segments (max(p_vaddr + p_memsz) - min(p_vaddr)). 2. A backing buffer (ElfProcessImage::image_buffer) is allocated from the kernel heap. 3. The load base base_addr is assigned to the pointer of this backing buffer. 4. Each segment's file contents (p_filesz) are copied to base_addr + p_vaddr. 5. Any remaining .bss bytes (p_memsz - p_filesz) are zeroed using core::ptr::write_bytes(). 6. The runtime entry point is computed as base_addr + header.e_entry. 7. Page table entries backing the segment buffer are updated with the USER_ACCESSIBLE bit (bit 2) so unprivileged Ring 3 instructions can read, write, and execute them without triggering #PF (Page Fault).

This ensures that even if user code corrupts its user stack, the microkernel operates safely on an isolated, verified kernel stack.

Zsh-Style Interactive Line Editor & History

The shell includes an interactive line editor (editor.rs): - Up / Down Arrow History Navigation: Traverses the command history buffer (history.rs). Pressing ↑ recalls previously entered commands, while ↓ cycles forward or restores the typed draft line. - Tab Auto-Completion (Zsh Style): Pressing Tab auto-completes built-in command names, aliases, and filesystem paths in the current directory. When multiple matches exist, a color-coded column listing is displayed, and the prompt and current editing line are cleanly reprinted. - In-Line Cursor Navigation: ← and → move the cursor anywhere within the line; Home jumps to the start, End jumps to the end. - In-Line Editing: Character insertion, Backspace, and Delete work anywhere in the line with automatic redraw. - History Expansion !!: Typing !! echoes and immediately re-executes the most recent command.

Terminal Scrolling via Scroll Lock & Arrows

Hydra implements classic PC terminal scrolling using the Scroll Lock mode and arrow keys:

  1. When Scroll Lock is Active ([SCROLL] Prompt): - The shell freezes command execution and converts navigation keys into terminal viewport navigation:

    • ↑ (Up Arrow): Scrolls the terminal screen UP line-by-line into the 512-line kernel scrollback buffer.
    • ↓ (Down Arrow): Scrolls the terminal screen DOWN line-by-line toward the active command prompt.
    • Page Up: Scrolls up by an entire screen page (rows - 2 lines).
    • Page Down: Scrolls down by an entire screen page.
    • Full Color & Attribute Preservation: The scrollback buffer tracks both character bytes and formatting attributes ((fg & 0xF) | ((bg & 0x7) << 4)). All syntax highlighting, prompt colors (LightCyan), section headers (Yellow), directory names (Green), and error messages (LightRed) are preserved verbatim when scrolling up and down.
    • When scrolled up into history, a cyan status banner displays the visible line range: -- SCROLL LOCK (up N lines, lines X-Y of Z) [UP/DOWN or PgUp/PgDn, ESC to exit] --.
    • Allows naturally reviewing long command outputs (like help, cat, ls -l, history, or kernel boot diagnostics) that scrolled off the top of the screen without losing any visual hierarchy.

  2. When Scroll Lock is Inactive (Normal Mode): - ↑ (Up Arrow) cycles backward through the command history ring buffer. - ↓ (Down Arrow) cycles forward through the command history ring buffer. - Typing any printable character, pressing Enter, or hitting Backspace automatically snaps the viewport back to the active prompt.

  3. Activating & Toggling Scroll Lock: - Keyboard Shortcut: Press Ctrl+S or F12 in the shell to immediately toggle Scroll Lock on/off. The prompt dynamically reflects the mode (hydra:/bin [SCROLL]> vs hydra:/bin>). - Direct Page Up: Pressing Page Up at the prompt automatically enables scrolling mode and pages up through previous screen contents. - Shell Command: Run scroll (or scroll on / scroll off) from the command line. - Exiting Scroll Mode: Press Escape, Ctrl+S, or Ctrl+C to return to normal prompt mode. - VirtualBox Note: In VirtualBox with UEFI enabled, the firmware's EFI_SIMPLE_TEXT_INPUT_PROTOCOL does not generate key events for the physical Scroll Lock key (and host OS keyboard hooks often intercept or discard it). Use Ctrl+S, F12, or scroll on inside the VM for instant, reliable scrolling.

3. Integrating New Commands & Standalone Programs

Hydra supports two complementary paradigms for adding commands and applications:

Approach A: Dynamic Filesystem Search ($PATH Discovery — No Code Changes!)

This is the recommended approach for integrating standalone applications, external utilities, and third-party binaries.

  1. How It Works: When a command is entered (e.g. hydra> matrix or hydra> test_app arg1 arg2), the shell first checks built-in commands. If not found, it dynamically searches the $PATH directories on the boot volume: - \bin\ - \apps\ - \EFI\BOOT\ - \ (root directory)

For each directory, it probes for: - <dir>\<cmd>.efi - <dir>\<cmd>

  1. Loading & Execution: - The file is located on the UEFI boot volume via SimpleFileSystem. - The binary's PE32+ header (MZ signature) is verified. - Memory pages are dynamically allocated and the executable is loaded via uefi::boot::load_image. - Arguments are passed through the UEFI LoadedImage protocol. - The process is executed via uefi::boot::start_image. - Upon termination, control returns immediately to the Hydra interactive shell prompt!

  2. Zero Kernel Modifications: You can drop any compiled UEFI PE32+ .efi executable into \bin\ or \apps\ on your boot USB or disk image at any time. You do NOT need to modify commands/mod.rs or recompile the kernel!

Approach B: Static Built-in Command Integration

Used for core microkernel primitives that require direct access to kernel internals, CapabilityTable, or ShellState.

Step 1: Create a New Command File

Create a new file in src/shell/commands/, e.g. src/shell/commands/my_tool.rs:

use crate::console::set_color;
use uefi::proto::console::text::Color;
use crate::shell::command::Command;
use crate::shell::state::ShellState;

pub struct MyToolCommand;

impl Command for MyToolCommand {
    fn name(&self) -> &'static str {
        "mytool"
    }

    fn aliases(&self) -> &'static [&'static str] {
        &["mt"]
    }

    fn description(&self) -> &'static str {
        "Demonstrates custom command integration"
    }

    fn usage(&self) -> &'static str {
        "mytool <argument>"
    }

    fn execute(&self, args: &[&str], state: &mut ShellState) {
        set_color(Color::LightGreen, Color::Black);
        println!("[+] MyTool executed with args: {:?}", args);
    }
}

Step 2: Register in src/shell/commands/mod.rs

In src/shell/commands/mod.rs: 1. Add the module: pub mod my_tool; 2. Export the struct: pub use my_tool::MyToolCommand; 3. Add &MyToolCommand to the COMMANDS slice: rust pub static COMMANDS: &[&dyn Command] = &[ ... &MyToolCommand, ];

4. Architecture & Key Features

Automatic 3-Second Bare-Metal Transition Countdown

Upon shell startup, Hydra automatically initiates a 3-second countdown before transitioning to bare-metal hardware ownership (exitboot): - Hands-Free Boot: Users no longer need to manually type exitboot to unlock Ring 3 user mode, autonomous framebuffer rendering, and preemptive multitasking. - Countdown Display: An interactive timer counts down (3... 2... 1... NOW), after which ExitBootServices is called, hardware ownership is established, and the bare-metal prompt hydra:/bin> appears. - User Control: - Pressing Enter during the countdown immediately bypasses the remaining delay and transitions to bare metal instantly. - Pressing any other key (e.g. Space or Esc) cancels the countdown, keeping the shell in UEFI Boot Services mode.

Thread-Safe Interactive Input & Automatic Prompt Refresh

Interactive input is handled by src/shell/editor.rs (read_line): - Automatic Prompt Appearance: When a command finishes execution, the shell REPL loop immediately formats and renders the hydra:/> prompt on screen without requiring the user to press Enter. - Foreground vs. Background Task Synchronization: Commands like spawn user, spawn rogue, spawn mutex, and spawn producer execute in the foreground by default using task::wait_task(id), returning CPU control and rendering the prompt precisely when task execution finishes. Passing --bg, -b, or & launches the task asynchronously in the background. - Asynchronous Prompt Auto-Refresh: If a concurrent background task (e.g. consumer receiving IPC messages) writes output to the console while the shell is waiting for input, get_key_or_refresh() monitors the global console generation counter (CONSOLE_OUTPUT_GENERATION). Once background output completes, the shell automatically moves to a new line and re-renders the prompt (and preserves any partially typed input) without requiring user intervention. - Real-time backspace support erases characters from screen and buffer seamlessly via cursor positioning. - Enter (\r or \n) submits the command line.

Multi-Tier Power Management (shutdown & reboot)

Virtual machine firmware (such as VirtualBox's EFI and QEMU/EDK2) frequently stubs or hangs on generic UEFI runtime ResetSystem(EfiResetShutdown) prior to ACPI table activation. Hydra solves this by implementing direct hardware I/O power transitions: 1. VirtualBox ACPI: Writes sleep state S5 bits to PIIX3/4 ACPI PM1a_CNT (I/O Port 0x4004). 2. QEMU ACPI: Writes to standard PIIX4 ACPI PM1a_CNT (I/O Port 0x604) and debug exit (0x501). 3. Cloud / Bochs ACPI: Writes to I/O Port 0xb004 and APM (0xb2). 4. Reboot Sequencing: Pulses the 8042 keyboard controller reset line (0x64, 0xFE) and the PCI reset control register (0xCF9, 0x06) before falling back to UEFI cold reset.
