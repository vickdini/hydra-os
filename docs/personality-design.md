# Programs from other systems: design (step 0)

Microkernel wave 4, Group 11, 2026-11-18. Base: `host-unit-tests` f5810fa. **No kernel or
linux-server code changes in this step**: this document, scripts under `tools/personality/`,
and test sources under `tests/freebsd/` and `tests/macos/`. The facts about FreeBSD and macOS
come from FreeBSD 15.1-RELEASE (`base.txz`, `src.txz`), XNU `xnu-12377.121.6` (macOS 26) and
Darling at commit 2649752 (2026-11-18), all downloaded and inspected for this report.

**Who this is for:** the user (technical, not a kernel specialist) and the agents of wave 5
(the personality hook), wave 10 (the core split), wave 11 (FreeBSD) and wave 12 (macOS).

The full per-call tables and the errno maps are in three companion files, generated by the
scripts: [personality-freebsd-syscalls.md](personality-freebsd-syscalls.md),
[personality-macos-syscalls.md](personality-macos-syscalls.md) and
[personality-errno.md](personality-errno.md).

## 0. The answer in brief

- **A personality is a property of a process,** chosen when it `exec`s a program: from the
  ELF OS/ABI byte (FreeBSD's binaries all say 9), the ELF ABI note ("FreeBSD"), or the
  Mach-O magic (macOS). Linux stays the default. Everything that differs between systems is
  selected by it: the system call table, how results come back, signal numbers and signal
  frames, the initial stack, and the address-space layout (section 2).
- **The hook (wave 5) is small:** about 1,000 lines of kernel code. The forwarding table
  becomes one table per personality, picked through a per-CPU pointer written at context
  switch, so a system call still costs **one table load**. The trap returns results in the
  personality's convention (Linux: `-errno`; FreeBSD and macOS: carry flag set and a
  positive errno, sometimes a second value in `rdx`). Wave 5 can prove it with a tiny
  static FreeBSD program (`tests/freebsd/rawsys.c`, already written) whose calls reach a
  FreeBSD table. Estimate **3–4 agent-days**, as the plan says.
- **Today a FreeBSD program is not refused, it is misread** (section 1.3): the loader ignores
  the OS/ABI byte and runs it as a Linux program with Linux system call numbers. FreeBSD's
  `write` (4) becomes Linux `stat`, its `exit` (1) becomes `write`, and a static FreeBSD
  program loops forever. The hook must fix this first, even before FreeBSD works.
- **FreeBSD against Linux (section 4):** of FreeBSD's **409 live system calls**, 125 map
  directly onto an existing Linux-layer operation, 117 need a layout or constant
  translation, 46 are new (kqueue, sysctl, `thr_*`, `_umtx_op`, Capsicum, jails, ...) and
  121 can be stubbed. Weighted by how many of the base system's 27,000 files use each call,
  the top 100 calls are 56 direct, 29 translated, 10 new and 5 stubs. FreeBSD's dynamic
  linker needs just **30 calls** to start a program: the natural first milestone.
- **FreeBSD preparation is done:** a checked 15.1 `base.txz`, a `/freebsd` root tarball
  (160 MB), the binaries' marking recorded, four test programs that cross-compile with
  clang against the extracted base, and milestones from `echo` to `pkg` and a Qt program on
  the KDE desktop (section 4.6).
- **macOS against the BSD core (section 5):** of XNU's 455 live BSD calls, 170 are the same
  operation as FreeBSD's, 74 need macOS layouts, 65 are macOS-only, 35 belong to a
  `mach-server` (pthread, workqueue, psynch) and 111 can be stubbed. Darling implements 291
  of them, plus 52 Mach traps.
- **Darling's bottom layer does not need rewriting, it can be dropped.** Darling translates
  macOS system calls into Linux system calls *inside* `libsystem_kernel` (39,060 lines of
  "emulation", 321 Linux system call sites), and sends Mach traps to `darlingserver` over a
  Unix socket. With a macOS personality in Hydra's trap, the original Apple stubs (XNU's
  `libsyscall`, which issue the real macOS system calls) work as they are, and the
  emulation directory goes away. The work moves into Hydra: a macOS front end and a
  `mach-server`. darlingserver (12,300 lines of its own, plus 66,500 lines of XNU's Mach
  code compiled in) is the obvious starting point for the mach-server (section 5.4).
- **Graphics for Mac programs are closer than the plan assumed:** Darling's AppKit has a
  Wayland back end (12,500 lines), so a Mac program could draw through the KDE compositor
  over a shared Unix socket, just like FreeBSD programs, once `libwayland-client` is built as
  a Mac library. Metal (Darling has an early Metal-on-Vulkan layer) stays out of reach.
- **What the kernel needs for macOS beyond the hook (section 6):** a Mach-O loader (about
  1,200 lines, in the kernel, like the ELF loader), a commpage at `0x7FFFFFE00000`, a
  different stack top (the commpage sits inside Hydra's default stack area), a 4 GiB
  `__PAGEZERO` floor, TLS in `%gs`, and system call classes in `rax`. No dyld shared cache:
  Darling's frameworks are separate files and dyld loads them one by one.
- **Estimates (section 7):** wave 5 hook 3–4 agent-days (confirmed); wave 10 core split
  **6–8** (was 5–7); wave 11 FreeBSD **21–28** (was 15–25; best split in two); wave 12
  macOS command-line programs **35–55**, with GUI programs a later wave on top.
- **Recommendation:** keep the order hook → core split → FreeBSD → macOS, but (1) put a
  **Wine milestone in wave 11**: FreeBSD has its own Wine package, so Windows programs on
  the FreeBSD front end are a cheap "Wine without Linux"; (2) treat a dedicated native Wine
  back end as worth less than that; (3) start macOS only after wave 11 proves the BSD core,
  with command-line programs first.

## 1. What a personality is on Hydra today

### 1.1 The facts in the code (f5810fa)

- **Every task has a `personality`** (`src/task/tcb.rs`, `TaskPersonality`): `Hydra` (native
  drivers, servers, hydra-shell) or `Linux`. Linux tasks get it where the kernel creates
  them (`src/task/scheduler.rs`, three places); `fork` and threads copy it.
- **The dispatcher** (`hydra_syscall_dispatcher`, `src/arch/syscall.rs`) asks
  `current_personality()` under the scheduler lock, then sends Linux tasks to
  `dispatch_linux_syscall` and the rest to the native calls. Before that:
  - `compat::linux::fast_syscall` answers `getpid`, `gettid`, the `getuid` family and
    private futex wakes without the kernel lock. It checks the personality only indirectly
    (its per-CPU cache is filled only for Linux tasks), but **it matches Linux numbers
    first**.
  - Wave 4's Group 10 adds `lx::fast_entry` in the same place: forwarded calls and
    `SYS_LX_REPLY_RECV` without the kernel lock. It also routes **by raw `rax`** before
    anything else.
- **The forwarding table** (`src/lx/mod.rs`) is one global `[AtomicU8; 512]`, indexed by
  the Linux number; Group 9 turns the byte into flags (`T_SERVER`, `T_FD0`, `T_IPC`,
  `T_UMASK`, `T_FDAT1`).
- **Results:** every Linux call returns `-errno` in `rax`. The trap never touches the carry
  flag; `sysret` restores the caller's `rflags` from the frame.
- **Signals:** numbers are Linux's; masks are `u64`; `rt_sigaction` keeps `SigAction
  { handler, flags, restorer, mask }` in the kernel; `build_frame` (`compat/linux/proc.rs`)
  writes Linux's `rt_sigframe` (`ucontext` 304 bytes, Linux `siginfo` 128 bytes, the FPU or
  XSAVE area) and returns through the program's own `sa_restorer`.
- **Exec:** `task::exec::load_linux_exec` maps the program and its `PT_INTERP`, builds
  an 8 MiB stack under `STACK_TOP` (`0x7FFF_FFFF_F000`) and Linux's auxiliary vector
  (`AT_SYSINFO_EHDR` points at Hydra's vDSO).

### 1.2 How FreeBSD binaries are marked (checked with readelf on 15.1)

| File | EI_OSABI | ABI note (`.note.tag`) | Interpreter |
|---|---|---|---|
| `/bin/sh` (PIE) | 9 (`ELFOSABI_FREEBSD`) | "FreeBSD", type 1 (`NT_FREEBSD_ABI_TAG`) = 1501000; type 4 (feature control) = 0; type 3 (arch tag) | `/libexec/ld-elf.so.1` |
| `/lib/libc.so.7` | 9 | "FreeBSD" type 1 = 1501000 | |
| `/libexec/ld-elf.so.1` | 9 | "FreeBSD" type 1 = 1501000 | (is the interpreter) |
| our clang-built tests | 9 | "FreeBSD" type 1 = 1501000 (from `crt1.o`; `rawsys` writes it itself) | `/libexec/ld-elf.so.1`, or none (static) |

- The byte and the note always agree in FreeBSD's own output and in clang's. FreeBSD's
  kernel accepts either; very old binaries (before 2003) carried only the "branding" in
  the byte. Go binaries for FreeBSD also set the byte.
- `1501000` is `__FreeBSD_version` (15.1). The C library asks for it (`AT_OSRELDATE`,
  `kern.osreldate`) to pick compatible behaviour, so the FreeBSD front end must report the
  version of the root it serves.
- **FreeBSD 15 moved every system call stub out of libc into `libsys.so.7`** (444
  `syscall` instructions there; libc has 6 left, the dynamic linker 30). That is FreeBSD's
  equivalent of macOS's `libsystem_kernel`: one library is the whole kernel interface.

### 1.3 What happens today with a FreeBSD program (read from the code)

`execve` never looks at `EI_OSABI` or the notes (`ElfBinary::parse` checks only class,
data, machine, type and program headers). So:
- **A dynamic FreeBSD program** in `/ubuntu`: the interpreter `/libexec/ld-elf.so.1` does
  not exist there, and `execve` fails with `ENOENT` (`ElfError::InterpreterNotFound`).
  This is the only "refusal", and it is an accident.
- **The same program in a root that has `/libexec/ld-elf.so.1`** (a `/freebsd` root): the
  kernel loads FreeBSD's dynamic linker as a Linux program. Its first system calls use
  FreeBSD numbers that mean something else to Linux (FreeBSD `__sysctl` 202 is Linux
  `futex`, `mmap` 477 is unassigned, `openat` 499 is unassigned, `issetugid` 253 is
  `inotify_add_watch`...). It dies or misbehaves in unpredictable ways.
- **A static FreeBSD program** like `rawsys`: `write` (4) runs as Linux `stat` on the
  pointer 1 (`-EFAULT`), and `exit(1)` runs as Linux `write(1, NULL, 0)`, which succeeds,
  so the program **spins forever**.
- **The wave 5 hook must therefore start by recognising the marking,** and until a FreeBSD
  table exists, refuse such programs with `ENOEXEC` instead of running them as Linux.

## 2. The hook (wave 5)

The hook changes no behaviour for Linux programs. It makes personalities a first-class
property and gives every later wave a place to plug in. Names below are proposals.

### 2.1 Personalities and where they live

```rust
// src/task/tcb.rs
pub enum TaskPersonality { Hydra = 0, Linux = 1, FreeBsd = 2, MacOs = 3 }
```

- **In the task:** `Task::personality`, as today, plus nothing else; the per-personality
  state (FreeBSD's 128-bit signal mask, macOS thread ports) lives where the personality's
  code lives.
- **Per CPU:** `CURRENT_PERS[cpu]: AtomicU8` and `CURRENT_TABLE[cpu]: AtomicPtr<Table>`,
  written by `Scheduler::switch_to` next to `CURRENT_TID` and `CURRENT_IDX` (both direct
  switch and normal switch go through it). The system call entry reads these instead of
  calling `current_personality()` (which takes the scheduler lock today).
- **In requests to servers:** one byte `pers` appended to `LxCall` (Groups 9 and 10 already
  agree to append-only changes; see NOTES.md, wave 4). A worker's front-end dispatch reads
  it first.

### 2.2 Choosing the personality at exec

`execve` (and the kernel's own program start, `admin::linux`) picks the personality from
the **main program's** file, before mapping it:

| Rule (first match wins) | Personality |
|---|---|
| Magic `0xFEEDFACF` (Mach-O 64), `0xCAFEBABE`/`0xCAFEBABF` (universal, with an x86_64 slice) | macOS (wave 12; until then `ENOEXEC`) |
| ELF, `EI_OSABI` = 9 | FreeBSD |
| ELF, `EI_OSABI` = 0, and a `PT_NOTE` with name "FreeBSD" and type 1 | FreeBSD |
| ELF, `EI_OSABI` = 0 or 3 (GNU/Linux), anything else | Linux |
| ELF, any other `EI_OSABI` (NetBSD 2, Solaris 6, OpenBSD 12...) | `ENOEXEC` |

- **The interpreter must agree:** a FreeBSD program's `PT_INTERP` must itself be marked
  FreeBSD (`ld-elf.so.1` is), else `ENOEXEC`. This stops a FreeBSD program from being
  started by Linux's `ld.so` and the other way round.
- **Scripts (`#!`)** take the interpreter's personality, as they do now.
- **Cost:** the first page of the file is already read; the note scan touches at most the
  first few program headers. No cost for Linux programs, which are decided by the byte.
- **An explicit choice:** the admin interface's "linux run" op (`ADMIN_LINUX_RUN`) gets a
  personality field, so hydra-shell can say "run this as FreeBSD" for tests; nothing else
  needs to choose. A separate loader process (as Darling's `mldr` does for Mach-O) is not
  needed for ELF; for Mach-O see section 6.1.
- **Until wave 11** the FreeBSD table is a stub table (section 2.9), so FreeBSD programs
  start, but only the hook test programs do anything useful.

### 2.3 The per-personality table

Today's `TABLE: [AtomicU8; 512]` becomes one table per personality:

```rust
// src/lx/table.rs (proposal)
#[repr(C, align(64))]
pub struct Table {
    pub entries: [AtomicU32; 1024],  // indexed by the personality's own call number
    pub len: usize,                  // numbers >= len: the personality's "unknown" rule
    pub pers: TaskPersonality,
}
// entry = route (bits 0-2) | flags (bits 3-15: Group 9's FD0, IPC, UMASK, FDAT1; RET2, INDIRECT, ...)
//         | arg (bits 16-31: the Linux number for LINUX_AS)
```

| Route | Meaning |
|---|---|
| `KERNEL` | The kernel answers (Linux: today's `dispatch_checked`; other personalities: their kernel-local handler, section 2.8) |
| `SERVER` | Forward to the POSIX server (today's linux-server, endpoint 0x29) |
| `MACH` | Forward to mach-server (wave 12; another instance of the same forwarding machinery on another endpoint) |
| `LINUX_AS` | **Bridge until wave 10:** run the in-kernel Linux call number `arg` with the same arguments, then encode the result in this personality's convention. Only for class-D calls (section 4) whose arguments need no translation |
| `ENOSYS` | Answer `ENOSYS` in the personality's convention without anything else (deliberate stubs) |
| `NOSYS` | Unknown number: `ENOSYS`, plus `SIGSYS` for FreeBSD (FreeBSD's `nosys` sends `SIGSYS` unless `kern.signosys=0`) |

**One load per system call.** The entry path becomes:

```rust
let t = CURRENT_TABLE[cpu].load(Relaxed);        // per-CPU line already read for CURRENT_TID
let e = if nr < t.len { t.entries[nr].load(Relaxed) } else { t.unknown };
```

The per-CPU pointer sits in the same cache line as `CURRENT_TID`, which the entry already
reads, so the cost compared with today's `TABLE[nr]` is one dependent load from a hot line,
and no lock. Group 10's lock-free `fast_entry` and `fast_syscall` must route through this
pointer instead of the raw Linux number; for a non-Linux task `fast_syscall` returns `None`
at once (one compare on `CURRENT_PERS`).

- **The Hydra (native) personality** gets no table: native calls keep their own `match`,
  and `CURRENT_TABLE` is null for native tasks (one test, already needed today to tell a
  worker's `SYS_LX_REPLY_RECV` (52) from Linux `getpeername` (52)).
- **macOS has four call classes** in the top byte of `rax`: 1 Mach traps, 2 BSD (Unix),
  3 machine-dependent (`thread_fast_set_cthread_self`), 4 diagnostics. For a macOS task
  the entry splits `rax` into class and number and indexes one of four small tables;
  the class decode is two instructions, only for macOS tasks.
- **FreeBSD indirect calls** `syscall` (0) and `__syscall` (198) take the real number from
  `rdi` and shift the arguments down by one; the entry handles them for the FreeBSD table
  (an entry flag `INDIRECT`). The seventh argument (FreeBSD allows 8 for `__syscall` on
  some calls) does not occur on amd64 for any call that matters.
- **The switch back** (`lx=kernel`) keeps working per personality: for Linux it sends the
  moved calls to the kernel as today; FreeBSD and macOS have no in-kernel implementation, so
  their `SERVER` entries are unaffected by it.

### 2.4 The result convention

After the call, the trap holds a result `r` in the internal convention (Linux's: `r < 0` and
`r > -4096` is `-errno`). The personality turns it into registers:

| Personality | Success | Failure |
|---|---|---|
| Linux, Hydra | `rax = r` | `rax = r` (negative) |
| FreeBSD, macOS BSD class | `rax = r`; carry flag clear; `rdx` = second result if the call has one, else unchanged | `rax = errno_map[-r]` (positive); carry flag set in the saved `rflags` |
| macOS Mach class | `rax = kern_return_t` (no carry flag) | same |
| macOS machdep class | as BSD | as BSD |

- **The carry flag** is bit 0 of the saved `rflags` in the system call frame (`sysret`
  loads `rflags` from `r11`, which the entry saved there). Setting it costs one `or`. The
  Linux path does not change.
- **Second result (`rdx`).** FreeBSD: the kernel returns `td_retval[1]`, which starts as the
  caller's `rdx`, so calls that set nothing leave `rdx` alone; FreeBSD's `libsys` does not
  read it for `fork`/`vfork`/`pipe2`. macOS: `fork` and `vfork` return `rdx = 1` in the child
  and `0` in the parent (XNU's `libsyscall` checks it), and `pipe` returns the two
  descriptors in `rax` and `rdx`. So an entry flag `RET2` says "the answer has a second
  value", carried back from the server as a second result word (an `LxReply.result2`
  appended in the syscall page), and written to `rdx` only then.
- **errno maps** are 512-byte tables (`[u16; 256]`, internal errno to personality errno;
  generated in [personality-errno.md](personality-errno.md)).
  FreeBSD and Linux agree on 1–34 except 11 (Linux `EAGAIN`, FreeBSD `EDEADLK`); from 35 on
  they differ (FreeBSD `EAGAIN` is 35). macOS agrees with FreeBSD up to 81 and differs
  above. Errors that exist only in BSD (`ENOTCAPABLE` 93, `ECAPMODE` 94, `EFTYPE` 79,
  `EAUTH` 80, `ENEEDAUTH` 81, `EDOOFUS` 88, macOS `EBADEXEC` 85, `EBADARCH` 86...) get
  internal numbers above 512 (`-(512 + n)`), which only BSD front ends return; the Linux
  encoder never sees them.
- **Restarts** stay internal (`ERESTARTSYS`, `ERESTART_RESTARTBLOCK` → `rip -= 2`, `rax =`
  the original number). For a macOS task, `rax` is restored with its class bits; for a
  FreeBSD indirect call, with 0 or 198.
- **ptrace and seccomp** run before routing and see the raw number; they stay Linux-only
  until a later wave (a FreeBSD task cannot install a Linux seccomp filter, and a Linux
  tracer of a FreeBSD process sees FreeBSD numbers, which is what FreeBSD's `truss` expects).

### 2.5 Signals

- **One internal numbering: Linux's** (the kernel's masks are `u64`, signal delivery and
  `SigAction` stay as they are). Each other personality has a pair of maps (128 bytes
  each) between its numbers and the internal ones:

  | FreeBSD/macOS | Internal (Linux) | Note |
  |---|---|---|
  | 1–6, 8, 9, 11, 13–15 | same | HUP INT QUIT ILL TRAP ABRT FPE KILL SEGV PIPE ALRM TERM |
  | 7 `SIGEMT` | 16 (`SIGSTKFLT`) | no Linux equivalent; Linux 16 is unused by Linux programs |
  | 10 `SIGBUS`, 12 `SIGSYS` | 7, 31 | |
  | 16 `SIGURG`, 17 `SIGSTOP`, 18 `SIGTSTP`, 19 `SIGCONT`, 20 `SIGCHLD` | 23, 19, 20, 18, 17 | |
  | 21–28 (`TTIN TTOU IO XCPU XFSZ VTALRM PROF WINCH`) | 21, 22, 29, 24–28 | |
  | 29 `SIGINFO` | 30 (`SIGPWR`) | Ctrl+T on BSD; a Linux receiver sees `SIGPWR` |
  | 30 `SIGUSR1`, 31 `SIGUSR2` | 10, 12 | |
  | FreeBSD 32 `SIGTHR`, 33 `SIGLIBRT` | 32, 33 | libthr's and librt's private signals (glibc reserves the same two) |
  | FreeBSD 65–95 (`SIGRTMIN`..) | 34–64 | 31 real-time signals; FreeBSD's 96–126 are refused (`EINVAL`) |

  A signal sent between personalities (a FreeBSD shell killing a Linux program) is
  translated at the sender's trap into the internal number, and at delivery into the
  receiver's: `SIGINFO` arrives as `SIGPWR`, which is the only lossy case that matters.
- **`sigaction` flags** are translated by the personality's kernel-local `sigaction`
  (FreeBSD `SA_ONSTACK 0x1, SA_RESTART 0x2, SA_RESETHAND 0x4, SA_NODEFER 0x10,
  SA_NOCLDWAIT 0x20, SA_SIGINFO 0x40, SA_NOCLDSTOP 0x8` against Linux's high bits).
  `SigAction` gets one more field: `pers` (which frame builder to use; a process has only
  one personality, but a handler installed before `exec` is reset anyway).
- **The frame builder becomes a per-personality function** called where `build_frame` is
  called today (`deliver_on_syscall_return`, `deliver_on_trap_return`):
  - **Linux:** today's `build_frame`, unchanged.
  - **FreeBSD:** `struct sigframe { sf_ahu (8); ucontext_t sf_uc; siginfo_t sf_si }`:
    `ucontext_t` is a 16-byte `sigset_t`, then `mcontext_t` (800 bytes: `mc_onstack`,
    `mc_rdi`..`mc_r15`, `mc_trapno`, `mc_fs`, `mc_gs`, `mc_addr`, `mc_flags`, `mc_es`,
    `mc_ds`, `mc_err`, `mc_rip`, `mc_cs`, `mc_rflags`, `mc_rsp`, `mc_ss`, `mc_len`,
    `mc_fpformat`, `mc_ownedfp`, the 512-byte FXSAVE area, `mc_fsbase`, `mc_gsbase`,
    `mc_xfpustate` (pointer to the XSAVE extension, written below the frame),
    `mc_xfpustate_len`), then `uc_link`, `uc_stack`, `uc_flags`. FreeBSD enters the
    **signal trampoline (`sigcode`) first**, not the handler: `rip` = the trampoline in
    the FreeBSD shared page (section 2.6), `rsp` = the frame, `rdi`/`rsi`/`rdx`/`rcx` =
    signal, `&sf_si` (or the code without `SA_SIGINFO`), `&sf_uc`, fault address. The
    trampoline calls `sf_ahu` and then `sigreturn(&sf_uc)` (417). About 250 lines.
  - **macOS:** `rip` = the `sa_tramp` the C library passed in `sigaction` (libc's
    `_sigtramp`), arguments `(handler, infostyle, sig, siginfo, ucontext, token)`; frame =
    macOS `__siginfo` (104 bytes) + `ucontext64` + `mcontext64` (exception state, thread
    state, `x86_avx_state64`). `sigreturn(uctx, infostyle, token)` (184). About 250 lines.
- **`sigreturn`** is per personality (Linux `rt_sigreturn` 15, FreeBSD 417, macOS 184),
  kernel-local, the inverse of the builder.
- **`sigaltstack`'s `stack_t`** differs (FreeBSD and macOS: `ss_sp, ss_size, ss_flags`;
  Linux: `ss_sp, ss_flags, ss_size`): translated in the kernel-local call.
- **Wave 5 builds** the maps, the dispatch points and the FreeBSD/macOS entries as
  `unimplemented → SIGKILL` (a stub that ends the process cleanly); the FreeBSD frame is
  wave 11 work.

### 2.6 The initial stack, the auxiliary vector and the address space

`load_linux_exec` gets a personality parameter (`ExecLayout`) that decides:

| | Linux (today) | FreeBSD | macOS (wave 12) |
|---|---|---|---|
| Stack top | `0x7FFF_FFFF_F000` | the same (FreeBSD's `USRSTACK` is one page lower; programs read it from `AT_USRSTACKBASE` or `kern.usrstack`) | `0x7FF7_FFFF_F000`: the commpage at `0x7FFF_FFE0_0000` lies **inside** Hydra's default stack area |
| Lowest mapping | `0x1_0000` | `0x1_0000` (FreeBSD forbids page 0 by default; no other floor) | **4 GiB** (`__PAGEZERO`): nothing is mapped below `0x1_0000_0000` |
| Stack contents | `argc, argv, envp, auxv` | the same order, **FreeBSD `AT_*` numbers**, plus `struct ps_strings` at the stack top (`AT_PS_STRINGS`) | the main executable's Mach-O header address, `argc, argv, envp`, then the `apple[]` strings (`executable_path=`, `ptr_munge=`, `main_stack=`, `stack_guard=`, `malloc_entropy=`, `th_port=`...), no auxv |
| Shared kernel page | vDSO (`AT_SYSINFO_EHDR`) | **shared page**: the signal trampoline (about 40 bytes), optionally `vdso_timekeep` (`AT_TIMEKEEP`); at `0x7FFF_FFFF_F000` | **commpage** at `0x7FFF_FFE0_0000`: signature, version, CPU capabilities, CPU counts, memory size, page shift (what Darling's `mldr` fills); later the time data |
| Interpreter | `PT_INTERP` (ld-linux) | `PT_INTERP` (`/libexec/ld-elf.so.1`) | `LC_LOAD_DYLINKER` (`/usr/lib/dyld`) |
| TLS register | `%fs` | `%fs` (`sysarch(AMD64_SET_FSBASE)`) | **`%gs`** (machdep call 3, `thread_fast_set_cthread_self`); Hydra already keeps a user GS base per thread for Wine |

**FreeBSD's auxiliary vector** (numbers from `sys/elf_common.h`; they collide with Linux's,
e.g. Linux 15 is `AT_PLATFORM` but FreeBSD 15 is `AT_EXECPATH`):

| Needed at once (rtld, libc) | Optional (libc falls back to a system call) |
|---|---|
| `AT_PHDR 3, AT_PHENT 4, AT_PHNUM 5, AT_PAGESZ 6, AT_BASE 7, AT_FLAGS 8, AT_ENTRY 9, AT_UID 11, AT_EUID 12, AT_GID 13, AT_EGID 14, AT_EXECPATH 15, AT_OSRELDATE 18, AT_NCPUS 19, AT_PAGESIZES 20, AT_PAGESIZESLEN 21, AT_STACKPROT 23, AT_EHDRFLAGS 24, AT_HWCAP 25, AT_HWCAP2 26, AT_BSDFLAGS 27 (= 0), AT_ARGC 28, AT_ARGV 29, AT_ENVC 30, AT_ENVV 31, AT_PS_STRINGS 32, AT_USRSTACKBASE 35, AT_USRSTACKLIM 36` | `AT_CANARY 16`/`AT_CANARYLEN 17` (else `kern.arandom`), `AT_TIMEKEEP 22` (else `clock_gettime`), `AT_FXRNG 33` (else `getrandom`), `AT_KPRELOAD 34` (the vDSO image, for unwinding through the trampoline) |

`AT_BSDFLAGS = 0` matters: without `ELF_BSDF_SIGFASTBLK`, rtld and libthr never call

### 2.7 fork, exec, threads and the crash policy

- **fork and threads** copy the personality (they already copy the field). A FreeBSD
  `thr_new` and a macOS `bsdthread_create` end in the same kernel thread creation as
  Linux's `clone` (later `task_clone`).
- **exec changes the personality** to the new program's (section 2.2). What crosses:
  - **descriptors** (the same core objects; a kqueue descriptor exec'd into a Linux
    program is a descriptor of an unknown kind there: `read` gives `EINVAL`, `close` works);
  - **signal dispositions:** handlers reset to default as always; *ignored* signals stay
    ignored, translated through the internal numbers;
  - **credentials, working directory, root, limits** (resource numbers are translated at the
    trap; the values are internal);
  - **personality-only state is dropped:** FreeBSD's `sigfastblock` word, `procctl`
    reaper state stays (it is process state in the core), macOS thread ports and the
    task's port space (mach-server is told by the exec notification).
  - **A FreeBSD program exec'ing a Linux one** (FreeBSD's `sh` running `/ubuntu/bin/ls` with
    a path that reaches the Ubuntu root) works: the kernel checks the new program's
    marking, not the caller's. Path roots are the core's business (section 3.5).
- **ptrace:** a Linux debugger may trace a FreeBSD process (it sees FreeBSD numbers and
  registers in Linux's `user_regs_struct`, which is just the registers). FreeBSD's own
  `ptrace` API (`PT_*`) is wave 11+ work.
- **The crash policy** today ends "every user task with the Linux personality" when
  linux-server dies. It becomes **every task whose front end lives in that server**:
  Linux, FreeBSD and macOS tasks (all three share the POSIX core). When **mach-server**
  dies, only macOS tasks end (their port rights are gone), and the supervisor restarts it.
- **Process IDs are shared:** one PID space for all personalities, so `ps` in any root sees
  every process (FreeBSD's `kern.proc` and macOS's `proc_info` are views of the core's
  process table).

## 3. The core split (wave 10)

By the end of wave 9 linux-server owns files, descriptors, sockets, pipes, processes and
signal policy. Wave 10 turns it into a **POSIX core with front ends**. No behaviour changes
for Linux programs.

### 3.1 What the core owns

| Area | Core object | Today's code (moved by waves 5–9) |
|---|---|---|
| VFS | path walk, mounts, roots (`/ubuntu`, `/freebsd`, `/macos`), file objects, page-cache objects (kernel) | `vfs`, `mount`, `fs`, `recent`, `extra`, `misc` |
| Descriptors | the descriptor table, close-on-exec, descriptor passing | `fs/fd.rs` |
| Sockets | Unix sockets, Internet sockets (as net-server's client), netlink only for Linux | `unix`, `socket`, `inet`, `sockopt` |
| Pipes, FIFOs, event objects | pipe buffers; eventfd, timerfd, signalfd, pidfd/procdesc; inotify | `fs/pipe.rs`, `eventfd`, `timerfd`, ... |
| Processes | the process table, sessions, process groups, credentials, wait/exit, resource limits, namespaces | `proc` policy, `process`, `execve`, `ns`, `limits` |
| Signals (policy) | who may signal whom, queued signal info, job control | `proc` |
| Readiness | readiness words per object, wait sets (section 3.4) | `select`, `epoll`, wave 4's readiness words |
| IPC | message queues, System V, POSIX named objects | `mqueue`, `sysv` |

**Core operations** are internal functions with neutral arguments (`OpenFlags`, `Stat`,
`SockAddr`, `Errno`, internal signal numbers). For the shared set, the operation numbering
reuses Linux's numbers, because that code came from the Linux layer and the Linux front end
then has nothing to renumber. Operations Linux lacks (kqueue, sysctl, attribute lists) get
numbers from 1024 up. This is a numbering choice, not a dependency: a FreeBSD call is
translated into a core operation with BSD semantics, never into a Linux system call with
Linux semantics. Where the semantics differ for the same operation, the operation takes the
caller's personality from `LxCall.pers`:
- FreeBSD and macOS **pipes are bidirectional**;
- a **kqueue is not inherited** across `fork` (an epoll descriptor is);
- `rename` over a directory, `O_APPEND` with `pwrite`, `unlink` of an open directory and
  similar corner cases follow the caller's system;
- `ENOTCAPABLE` exists only for Capsicum.

### 3.2 What a front end does

- **Decode:** number → core operation (the table of section 2.3, server side).
- **Translate layouts and constants in and out:** `stat`/`stat64`, `statfs`, `dirent`,
  `sockaddr` (with `sa_len`, family numbers: `AF_INET6` is 10 on Linux, 28 on FreeBSD, 30
  on macOS), `msghdr`/`cmsghdr`, socket options, `fcntl` commands and `struct flock`,
  `ioctl` numbers per device, open/`AT_*`/`mmap`/`MSG_*` flags, clock ids, resource
  numbers, signal numbers and masks, `siginfo`, `sigevent`, `rusage`, `termios`.
- **Personality-only calls:** Linux's `epoll`, `inotify`, `io_uring`, netlink; FreeBSD's
  `sysctl`, `kqueue`, Capsicum, jails, `procctl`, `kenv`, `extattr_*`; macOS's
  `getattrlist`, `proc_info`, `csops`, guarded descriptors, `posix_spawn`.
- **Its own view of the system:** `/proc` for Linux; `sysctl` and `kern.proc` for FreeBSD;
  `proc_info` and `sysctl` for macOS. All read the same core process table.

Expected size: the Linux front end is the Linux-specific half of today's code (layouts,
netlink, epoll, io_uring, /proc); the FreeBSD front end is new, about 9,000–12,000 lines
(section 4.5); the macOS front end reuses the FreeBSD one's BSD translations and adds
about 6,000–9,000 lines.

### 3.3 How the split is done

Doing all 45,000 lines at once is not needed. Wave 10 builds:
1. the core operation interface and the front-end dispatch in linux-server (`pers` in
   `LxCall`, one `match` per personality);
2. the neutral types (`OpenFlags`, `Stat`, `SockAddr`, `Errno`, `SigSet`) and Linux's
   encoders, moving the Linux layouts out of the core code;
3. the split of the about 120 operations that FreeBSD's base system uses most (files,
   descriptors, processes, signals, sockets, pipes, time): the "D" and "T" rows with the

The rest is split when wave 11 or 12 first needs it. **6–8 agent-days** (the plan says 5–7);
the extra day is the neutral types, which touch every moved file.

### 3.4 Where readiness, kqueue and epoll meet

Wave 4 (Group 9) gave every server object a **readiness word** in memory shared with the
kernel (`[poll bits, edge count, size]`), a "changed" bitmap and a doorbell. After wave 9
every descriptor is a core object with such a word. On top:
- **One wait-set engine in the core:** a set of (object, interest, user data, flags:
  edge/level/oneshot/dispatch) entries; when an object's word changes, the engine queues the
  matching entries to the set's ready list and wakes its waiters.
- **`epoll`** (Linux front end) and **`kqueue`** (FreeBSD and macOS front ends) are two
  encodings of the same engine:

  | kqueue filter | Engine source |
  |---|---|
  | `EVFILT_READ`/`EVFILT_WRITE` | readiness word bits; `data` = bytes available (the word's `size` field, or a call to the object for sockets) |
  | `EVFILT_TIMER` | a core timer (`timer_arm`) |
  | `EVFILT_SIGNAL` | the process's signal state (counts signals even if ignored, unlike `signalfd`) |
  | `EVFILT_PROC` (`NOTE_EXIT`, `NOTE_FORK`, `NOTE_EXEC`) | process-table events (what pidfd and `waitid` use) |
  | `EVFILT_VNODE` | the inotify machinery |
  | `EVFILT_USER` | a user-triggered flag |
  | `EVFILT_PROCDESC` (FreeBSD) | process descriptor (= pidfd) |
  | `EVFILT_MACHPORT` (macOS) | a port-set's readiness word owned by mach-server (section 5.4) |

- **Cross-personality use works naturally:** a Linux program's `epoll` on a socket shared
  with a FreeBSD program sees the same word.
- `EV_CLEAR` maps to edge-triggered, `EV_ONESHOT` to one-shot, `EV_DISPATCH` to "disable
  after delivery"; the kqueue `udata` and the epoll `data` are the same 64-bit field.
- `kevent`'s change list and event list in one call is a loop over the engine's add/remove
  plus one wait: no new kernel primitive.

### 3.5 Shared Unix sockets: Wayland and D-Bus for FreeBSD and Mac programs

The goal: a FreeBSD Qt program or a Mac program draws through the KDE compositor
(`kwin_wayland`) and talks to the session bus, like a Linux program.
- **One socket namespace:** Unix sockets bound to a path are core objects reached through
  the VFS; a FreeBSD program connecting to `/run/user/1000/wayland-0` reaches the same
  object as a Linux one, if the path resolves to the same file.
- **Roots:** a FreeBSD program runs chrooted in `/freebsd`. The core mounts the shared
  runtime directories into each root (`/run/user/UID`, `/tmp/.X11-unix`, `/var/run/dbus`):
  bind mounts, which the Linux layer already supports. FreeBSD's ports put the system bus at
  `/var/run/dbus/system_bus_socket` too.
- **`sun_len` and paths:** BSD `sockaddr_un` has `sun_len` and a 104-byte path (Linux:
  108). The front end strips or adds `sun_len`. Linux's abstract namespace (a leading NUL)
  does not exist on BSD; FreeBSD programs never use it, and Linux programs reaching a BSD
  socket use paths.
- **Credentials:** D-Bus's `EXTERNAL` authentication on FreeBSD uses `LOCAL_PEERCRED`
  (`struct xucred`) or `getpeereid`, and sends `SCM_CREDS` (`struct cmsgcred`). Linux uses
  `SO_PEERCRED` (`struct ucred`) and `SCM_CREDENTIALS`. The core keeps the peer's
  credentials with the socket (as it does today); each front end encodes its own form.
- **Descriptor passing (`SCM_RIGHTS`)** has the same meaning everywhere; `cmsghdr` layout
  differs (BSD: `socklen_t cmsg_len`, 4-byte alignment on macOS) and is translated.
- **Wayland's shared memory buffers:** FreeBSD's `libwayland` uses `memfd_create` (FreeBSD
  13+: `shm_open2(SHM_ANON)`), which the core maps onto its anonymous memory objects; the
  compositor mmaps the received descriptor as today.
- **Graphics drivers:** a FreeBSD Mesa needs a DRM device (`/dev/dri/*`) with FreeBSD's
  `ioctl` encoding of the same DRM commands; with Hydra's software rendering path (what KDE
  uses in a VM) Qt and GTK draw into shared memory buffers and need no DRM at all.

### 5.3 How Mach maps onto Hydra's IPC

| Mach | Hydra |
|---|---|
| A trap from a macOS task (class 1) | The forwarding machinery of wave 3 (syscall page, direct switch, workers), with a second server endpoint (proposal `0x2A`) and its own worker pool. Route `MACH` in the macOS class-1 table |
| Port names (per-task integers), rights, port sets | mach-server's tables (XNU's `ipc_space`/`ipc_entry` code, as darlingserver runs it) |
| `mach_msg` send, inline data | the copy-in table (wave 4, Group 10) for the header and small bodies; `SYS_LX_READ` beyond 3 KiB |
| `mach_msg` receive that blocks | answer `PENDING`, finish later with `SYS_LX_COMPLETE` (wave 4) |
| Out-of-line memory (`MACH_MSG_OOL_DESCRIPTOR`, copy-on-write semantics) | small regions copied by mach-server; large ones moved with page grants (syscalls 33/34) into the receiver with `as_map` of a copy-on-write object (design 5.2's `as_*`/`obj_*` primitives, wave 7–8) |
| Port rights in messages, `fileport_makeport/makefd` | mach-server's tables; a descriptor sent as a port is a pinned core descriptor (Group 9's `LX_OBJ_PIN`) |
| Dead-name and no-senders notifications | mach-server, plus the kernel's process-exit notification (`LX_NOTE_EXIT`) forwarded to it |
| Port sets in `kevent` (`EVFILT_MACHPORT`), libdispatch's run loop | a readiness word per port set in mach-server's window, read by the core's wait-set engine (section 3.4), as net-server does for sockets |
| Semaphores, `ulock` | mach-server first; futex words in the kernel when it matters |
| Thread ports and `thread_get_state`/`set_state` | mach-server, with `task_regs` (design 5.2) for the registers |
| Task ports and `vm_read`/`vm_write` of another task | mach-server, with the client memory primitives extended to a target process (today they reach only callers with a request in flight) |

**What would have to change for Hydra:**
- **Nothing in libsystem_kernel needs rewriting, if Hydra has a macOS personality.** The
  whole `emulation` directory exists to turn macOS system calls into Linux ones. With the
  hook, the trap takes macOS calls (class bits and all) and routes them to the macOS front
  end and mach-server. The stubs come from XNU's own `libsyscall`, unmodified, which
  Darling's build already compiles. So: **drop 39,060 lines, write the equivalent server
  side in Hydra** (the macOS front end, section 3.2, and mach-server). Darling's
  `vchroot` and `libkqueue` also go (Hydra's core has real roots and real kqueue).
- **Keeping Darling's emulation and pointing it at Hydra** (replacing its 321 Linux call
  sites with calls to Hydra's Linux personality) would work sooner, but puts Linux back in
  the path; it is the macOS equivalent of the FreeBSD shortcut the plan rejects.
- **mach-server:** darlingserver is the natural start. Its Linux-specific parts are small
  and localized: epoll (35 sites, 3 files), eventfd (16, 1 file), timerfd (6), signalfd (4),

  machinery, notifications and the client memory primitives. The XNU code and the
  microthreads stay. **The real obstacle is the language runtime:** darlingserver is C and
  C++ with libc and libc++, and Hydra's native servers are `no_std` Rust on `hydra-rt`.
  Three ways:
  1. **A C runtime for native servers** (a small libc on `hydra-rt`, plus libc++): useful
     beyond mach-server, but a project of its own (10+ agent-days).
  2. **mach-server as a FreeBSD-personality program** after wave 11: FreeBSD's libc and
     libc++ are in `/freebsd`, darlingserver's Linux parts become kqueue/procdesc, and it
     reaches Hydra's IPC through a **native escape** in the FreeBSD table (a reserved call
     class for registered service processes). Cheapest if wave 11 is done.
  3. **A Rust reimplementation** of the Mach IPC subset on `hydra-rt` (ports, rights, port
     sets, messages with OOL and port descriptors, notifications, semaphores, timers, the
     MIG subset of 5.2): 15–25 agent-days, and the history of Darling's own first attempt
     (an in-kernel reimplementation they abandoned for duct-taped XNU) says it is harder
     than it looks.

## 6. What the kernel needs beyond the hook

### 6.1 Mach-O loading: in the kernel

- **The kernel loads the main program and dyld**, exactly as it loads an ELF program and
  `ld.so`; dyld does everything else (libraries, binding, initializers), as on macOS.
  Darling instead runs `mldr`, an ELF program that loads the Mach-O file into its own
  process: on Hydra that would need a Linux or native ELF loader process, i.e. Linux in the
  path. The kernel loader is about **1,200 lines**: the Mach-O header and universal (fat)
  headers (pick the x86_64 slice; refuse arm64-only with `EBADARCH`), `LC_SEGMENT_64`
  (map with `initprot`/`maxprot`, file offsets, zero-fill), `__PAGEZERO`,
  `LC_LOAD_DYLINKER`, `LC_MAIN`/`LC_UNIXTHREAD`, slide for `MH_PIE`, code signature load
  command skipped, the stack of section 2.6, the commpage. Mapping uses the same
  `MappedObject` page-cache objects as the ELF loader.
- **dyld finds `LC_MAIN` itself**; the kernel passes the main header's address on the stack.

### 6.2 The dyld shared cache

Not needed. macOS 11+ ships its system libraries only inside the shared cache, but
Darling builds every framework as a separate dylib, and its kernel side answers
`shared_region_check_np` with "no shared region", so dyld loads files one by one. Hydra does
the same. A shared cache only matters for running Apple's own framework binaries, which
cannot be shipped anyway.

### 6.3 The commpage

- At `0x7FFF_FFE0_0000` (`_COMM_PAGE64_BASE_ADDRESS`), read-only, one page for data
  (Darling fills signature, version, CPU capabilities, CPU counts, memory size, page shift)
  and, on real macOS, a text page with the "preemption-free zone" routines that
  `OSAtomicFifoEnqueue` jumps into. Darling's libplatform does not use them; Hydra uses
  Darling's libplatform, so the data page suffices.
- **Address conflict:** Hydra's main stack today is `STACK_TOP - 8 MiB .. STACK_TOP` =
  `0x7FFF_FF7F_F000 .. 0x7FFF_FFFF_F000`, which contains `0x7FFF_FFE0_0000`. macOS tasks need
  their stack lower (section 2.6). The Linux vDSO and the FreeBSD shared page are placed by
  the kernel and announced in the auxv, so they do not conflict.
- **Time:** macOS `mach_absolute_time` and `gettimeofday` read time data from the commpage
  on real macOS; Darling's libSystem uses system calls instead. A later optimisation can
  fill the commpage time fields from Hydra's vDSO data.

### 6.4 The low address space (checked against Wine's work)

- Wine's work (2026-11-12, 642aa71/7893778) made the 1 GiB slots of the first 512 GiB
  belong to the process except where the kernel's image, heap, firmware or devices are
  (`KERNEL_LOW_SLOTS`, `src/memory/vm.rs`). Slots 2–3 (`0x8000_0000..0x1_0000_0000`) are
  always the kernel's; on q35 with 4 GiB the kernel image is at `0x1_4000_0000` (slot 5),
  the known `lowmem` failure.
- **macOS:** `__PAGEZERO` reserves `0 .. 0x1_0000_0000` (a protection, nothing is mapped,
  so the kernel's slots 2–3 there do not matter) and raises the process's lowest mapping
  to 4 GiB. **Every PIE Mach-O** (all modern programs and all dylibs) can be placed in the
  main user area (`>= 0x80_0000_0000`), avoiding the low slots completely. Only old
  non-PIE executables linked at `0x1_0000_0000` (slot 4) need that slot, which may be the
  kernel's on machines with more than about 3 GiB of RAM: the same condition as Wine's
  `0x1_4000_0000`, with the same fix (the kernel's low slots moved away).
- **FreeBSD:** non-PIE executables are linked at `0x20_0000` by lld (our test programs:
  checked) or `0x40_0000` by GNU ld: slot 0, always the process's. FreeBSD 15's base is PIE.
- **TLS in `%gs` for macOS** uses the per-thread user GS base Hydra keeps for Wine
  (`arch_prctl(ARCH_SET_GS)` in `compat/linux/ldt.rs`); the machdep call is a thin wrapper.

### 6.5 A native escape (reserve now, use later)

A process with a non-Linux, non-native personality cannot make Hydra's native system
calls (the numbers collide). If a server is ever built as a FreeBSD program (mach-server,
option 2 of 5.4), it needs them. Proposal: for FreeBSD and macOS tables, `rax` values with
bit 30 set are native Hydra calls (`rax & 0xFFFF`), allowed only for tasks registered as a
service. Wave 5 reserves the bit (returns `ENOSYS` for it) so nothing else uses it.

### 7.2 Changes to the plan

1. **Make the hook refuse what it cannot run.** Today FreeBSD programs run as Linux
   programs and misbehave (1.3). Wave 5's first commit should recognise the marking and
   return `ENOEXEC` until the FreeBSD table exists.
2. **The hook includes the result encoder and the exec layout switch**, not only the
   table: the plan's wave 5 list has the table, the result convention and signals; add
   the `ExecLayout` switch (auxv and stack), which the test program needs to start.
3. **The `LINUX_AS` bridge route** lets wave 5's test (and any early FreeBSD experiment)
   reuse in-kernel Linux code for the 125 direct calls without translating anything in
   the server. It disappears when the calls move into the core (waves 7–10). It is not
   the rejected "FreeBSD shortcut": it is only for calls whose meaning is identical.
4. **Wave 10 splits lazily** (3.3): the framework and the most-used operations; the rest
   when a front end needs them.
5. **Split wave 11 into 11a and 11b** (4.5).
6. **Add a Wine milestone to wave 11b** (7.3).
7. **Decide mach-server's runtime at wave 12's start** (5.4): FreeBSD-personality
   darlingserver is cheapest after wave 11.
8. **macOS GUI is a separate wave after 12**, through Wayland, not through a new display
   server.

### 7.3 Wine: a native back end before macOS?

- Windows programs already run under Wine on the Linux personality. A **native Wine back
  end** (Wine's Unix side talking to the POSIX core or to Hydra directly) would remove
  Linux from Wine's path, but Wine's Unix side is written against a POSIX C library: in
  practice "native" means building Wine against some libc that talks to Hydra.
- **FreeBSD is that libc.** Wine supports FreeBSD (`pkg install wine`), including its
  low-address and LDT needs, which Hydra already meets for the Linux Wine. Once wave 11b
  works, Windows programs on the FreeBSD front end are a Wine without Linux, at almost no
  extra cost: one milestone (`wine cmd /c ver` in `/freebsd`).
- A truly native back end (Wine's `ntdll` Unix side rewritten for Hydra's IPC, NT
  synchronization objects as kernel objects) is a large project (30+ agent-days) whose
  main gain would be speed; the Linux path's speed problems (Wine's synchronization) are
  better solved with an `ntsync`-like kernel primitive usable by every Wine.
- **Judgement:** yes, Windows programs without Linux should come **before macOS**, but via
  Wine on the FreeBSD front end (wave 11b), not a separate native back end. macOS then
  follows with command-line programs, as planned.

## 8. Risks and what was not verified

- **Nothing here ran on Hydra or on FreeBSD.** The test programs were compiled and
  inspected, not run. The classification of the 409 + 455 calls is by reading the tables,
  headers and man pages, not by running programs; expect a few calls to move between
  classes when wave 11 implements them.
- **Usage counts** are from dynamic imports of the base system; static binaries (`/rescue`)
  and calls made through `syscall(2)` are not counted, and ports (`pkg` packages) were not
  examined.
- **The `LINUX_AS` bridge** relies on the in-kernel Linux code until wave 10; if waves 7–9
  move a bridged call to the server, its table entry changes to `SERVER` with the same
  meaning.
- **The macOS front end's size** is an estimate from Darling's emulation (21,914 lines for
  the BSD calls on Linux, much of it conversions that the core split makes shared).
- **mach-server's runtime** (5.4) is the largest open question for macOS.
- **Apple's licences:** Darling's frameworks are open source (APSL, GPL); Apple's Command
  Line Tools and any App Store program must be fetched by the user, not shipped.
